레포부터 확인했어. 세 가지 다 확인은 됐는데, 1번은 이미 반쯤 되어 있고 2번은 레포 자신이 원인을 이미 진단해둔 상태더라. 스펙 초안이야.

## 만드는 것
컨텍스트 경고 3개 임계값(WARN·DANGER·HANDOFF)을 이름 그대로 하나의 손잡이로 만들고, 300k 초과 뒤에도 계속 진행되는 걸 실제로 막는 수단을 추가하고, 상태줄에 현재값·임계값을 같이 표시한다.

## 동작 계약
1. **임계값 설정** — 사실 이미 다 환경변수다. `WARN`·`DANGER`는 `statusline/ctx-warn-statusline.sh:50-51`, `HANDOFF`는 `woobin-harness/hooks/ctx-handoff-stop.sh:24`가 `${VAR:-기본값}`로 읽는다. 다만 `CTX_DANGER_THRESHOLD`(상태줄 ⛔ 표시)와 `CTX_HANDOFF_THRESHOLD`(실제 자동 핸드오프 트리거)가 서로 다른 변수인데 기본값만 우연히 같다(둘 다 300000) — 하나만 바꾸면 상태줄 표시와 실제 발동 시점이 어긋난다. → [?1]
2. **강제 수단** — `ctx-handoff-stop.sh`는 Stop 훅이라 턴이 끝날 때 `exit 2`로 세션당 1회만 넛지한다(43~46행 마커). 그다음 사용자가 그냥 프롬프트를 계속 치면 아무 것도 막지 않는다 — 지금 겪는 "무시하고 계속 감"이 정확히 이 틈이다. → [?2]
3. **상태줄 표시** — 지금은 danger/warn 구간에서도 현재값(`{k}k`)만 나오고 임계값 숫자는 안 보인다(`ctx-warn-statusline.sh:56-62`). 색으로만 "지금 위험 구간"을 알 수 있다. → [?3]

## 손대는 자리
- `statusline/ctx-warn-statusline.sh:50-62` — DANGER 변수 정리(1번), 출력 포맷에 임계값 추가(3번)
- `woobin-harness/hooks/ctx-handoff-stop.sh` — 마커를 새 훅과 공유(2번)
- `woobin-harness/hooks/ctx-handoff-guard.sh` (신규) — UserPromptSubmit, 마커 있으면 차단(2번)

- `docs/workflow-spec.md` §3 R13 + §4 훅 인벤토리·조정 손잡이 표(지금 `CTX_WARN_THRESHOLD`/`CTX_DANGER_THRESHOLD`가 표에서 빠져 있음) — CLAUDE.md 규약상 필수
- `scripts/test-hooks.sh` — 신규 훅 fixture (레포 규율: 훅마다 결정론적 분기 테스트)
- 두 `plugin.json` 버전 (CLAUDE.md 규약: 훅 개수 변경 시)

## 하지 않는 것
- 임계값을 바꾸는 CLI/명령어(`/ctx-threshold set` 같은 것) — 요청에 없음, 기존 env var 관례 유지
- 상태줄 색상 체계 재설계 — 숫자만 추가, 배색은 그대로
- IDLE_* 등 컨텍스트 경고와 무관한 다른 손잡이는 안 건드림

## 미결

**[?1] DANGER와 HANDOFF 임계값을 하나로 합칠지**
- A. 독립 유지 — 지금처럼 두 변수 그대로 두고, 문서(조정 손잡이 표)에 "같이 맞춰라" 주석만 추가한다. 다운스트림: 코드 변경 없음. 하지만 `CTX_HANDOFF_THRESHOLD`만 바꾸면 상태줄은 여전히 300k에서 ⛔가 뜨는데 실제 강제 핸드오프는 다른 값에서 발동 — 표시와 실제 동작이 어긋나는 상태를 그대로 남긴다.
- B. 통합 — `CTX_DANGER_THRESHOLD`를 없애고 상태줄도 `CTX_HANDOFF_THRESHOLD` 하나만 읽는다(WARN은 순수 표시용이라 그대로 독립). 다운스트림: 값 하나만 바꾸면 상태줄 표시와 실제 트리거가 항상 일치, 어긋날 수가 없어진다. 코드 변경은 `ctx-warn-statusline.sh` 한 줄.
- 추천: B. `ctx-handoff-stop.sh` 자신의 주석이 이미 "세 곳이 다른 값을 말하면 사용자가 어느 쪽을 믿을지 몰라진다"는 원칙을 쓰고 있다(원래는 ctx 계산식 얘기지만 임계값에도 같은 논리가 적용됨).

**[?2] 300k 넘은 뒤 강제 수단의 강도**
- A. 소프트 block — `idle-return-guard.sh`와 같은 패턴. 핸드오프 마커가 있으면 다음 프롬프트를 1회 막되, 같은 프롬프트를 10분 내 재제출하면 통과시킨다. 다운스트림: 사용자가 원하면 결국 뚫고 지나갈 수 있다 — 그런데 지금 문제 자체가 "재제출하듯 그냥 계속 감"이라, 이 패턴은 원래 막으려던 행동을 한 스텝만 늦출 뿐이다.
- B. 하드 block — 핸드오프 마커가 있는 한 그 세션의 모든 새 프롬프트를 예외 없이 막는다. `/clear`만 탈출구. `docs/workflow-spec.md`의 R13 무효화 조건이 이미 "재측정에서 핸드오프 문서가 만들어졌는데도 사용자가 `/clear`하지 않는 비율이 높으면, 그때는 개입 형태를 block(토큰 0 강제 정지)으로 바꾸는 게 맞다"고 적어뒀고, 지금 상황이 정확히 그 조건이다. 다운스트림: 확실히 붙잡지만, 핸드오프 문서가 부실하면 다음 세션이 되묻는 비용이 그대로 생긴다(R1과 같은 실패모드) — 그래서 handoff 스킬의 문서 완결성이 더 중요해진다.
- 추천: B. 레포가 이미 이 상황을 예견하고 처방까지 적어뒀다.

**[?3] 상태줄 포맷**
- A. 다음 관문 하나만 — `ctx 215k/300k`처럼 지금 넘어야 할 다음 임계값 하나만 붙인다. 다운스트림: 문자열이 짧다. 다만 WARN(200k) 값 자체는 텍스트로 안 보이고 색으로만 표시된다.
- B. 둘 다 상시 표시 — `ctx 215k (경고200k·위험300k)`처럼 항상 두 임계값을 같이 보여준다. 다운스트림: "지금 몇 k고 임계값이 뭔지"가 항상 한 줄에 다 보인다(요청 그대로). 문자열이 조금 길어져 좁은 터미널에서는 줄바꿈될 수 있다.
- 추천: B. 요청이 "지금 몇 k인지랑 임계값이 같이"라고 명시했다.
