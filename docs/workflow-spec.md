# 워크플로우 명세 — 리뷰용 전문

작성 2026-08-08 · 대상 독자: **미래의 프론티어 모델**

`workflow.html`은 사람이 보는 요약이다. 이 문서는 그 요약이 의도적으로 버린 것 — 각 규칙이
**어떤 측정에서 나왔고, 무엇을 대가로 치르며, 무엇이 참이 되면 지워야 하는지** — 를 담는다.
용도는 하나다: 모델이 세대를 넘었을 때 이 문서를 통째로 주고 재검토를 시키는 것.

---

## 0. 리뷰 프로토콜 — 이 문서를 받은 모델에게

세 가지를 판정해달라. 각 항목에 **§3의 규칙 ID(R1~R12)** 를 붙여서 답하라.

| # | 판정 | 판정 방법 |
|---|------|-----------|
| ① | **폐기 후보** | §3 각 규칙의 `무효화 조건`을 지금 환경에 대입한다. 참이면 그 규칙은 순수 오버헤드다 |
| ② | **부실 근거** | 근거 날짜가 오래됐거나 표본이 1~2 세션인 규칙. §8에 이미 아는 것만 적어뒀다 — 그 밖의 것을 찾아라 |
| ③ | **미사용 레버** | 그 시점 하네스에 있는데 여기서 안 쓰는 기능. 2026-08 기준으로 이미 3개를 이렇게 발견했다(§7-B) |

**증거 기준.** 이 하네스의 모든 규칙은 로컬 실측(세션 트랜스크립트 전수 분석)에서 나왔다.
반증도 같은 급으로 해라 — "요즘은 이렇게 한다", "베스트 프랙티스는" 류의 출처 없는 서술은 기각한다.
1차 출처(툴 설명 원문, 플랫폼 문서, 바이너리 확인)와 블로그를 구분해라. 실제로 이 하네스는
"플랜 모드가 탐색을 자동 위임한다"는 블로그 서술을 툴 설명 원문 확인으로 뒤집은 적이 있다(R5).

**주의 — 근거가 틀려도 규칙은 맞을 수 있다.** 2026-07-28에 스크린샷 위임 규칙의 근거 수치가
50~100배 과장(base64 글자수를 토큰수로 환산)인 게 드러났지만, 규칙 자체는 유지가 옳았다.
근거를 고치고 규칙은 **따로** 재평가해라. 근거 반증 = 규칙 폐기가 아니다.

**폐기를 권할 때는 대체물을 같이 내라.** 이 하네스의 규칙은 대부분 "소프트 지시로는 안 막혀서
구조를 바꾼 것"이다(§6-2). 규칙만 걷어내면 원래 문제가 그대로 돌아온다.

## 1. 환경 전제 — 이게 바뀌면 규칙이 흔들린다

이 워크플로우는 아래 조건에서 튜닝됐다. **리뷰 시 제일 먼저 각 항목의 현재 값을 확인해라.**

| ID | 전제 | 2026-08-08 값 | 어떤 규칙이 여기 매달려 있나 |
|----|------|---------------|------------------------------|
| E1 | 컨텍스트가 **요청마다 캐시 리드로 재청구**된다 | 그렇다. 실측에서 세션 비용의 66~72%가 cache read | R1·R2·R3·R6·R7 — **하네스의 절반** |
| E2 | 컨텍스트에 한 번 들어온 건 **안 나간다**(선택적 축출 없음) | 없다. `/clear`가 유일한 배출구 | R1·R2·R4·R5 |
| E3 | 프롬프트 캐시 TTL | 1시간 (이 세션 기준) | R6 (idle 핸드오프) — 전적으로 |
| E4 | 서브에이전트는 **부모 프리픽스를 공유하지 않는다** | 각자 새로 쓴다 | R8 (팬아웃 금지), 모드 ①의 순차 스폰 |
| E5 | 서브에이전트 `model` 미지정 시 **부모 상속** | 그렇다(기본값 `inherit`) | R3 |
| E6 | 모델 티어 간 가격차가 유의미 | opus ≫ sonnet ≫ haiku | R3, 모드 3종 전부 |
| E7 | effort 값이 **렌더된 프롬프트에 들어간다** → 세션 중 변경 시 프리픽스 무효화 | 그렇다 | R7 |
| E8 | 모델이 **이미 자기검증을 한다** → 명시적 검증 지시는 over-verification | Opus 5 문서 명시 | R9 |
| E9 | 컨텍스트 창 | 1M (Opus 5 1M 컨텍스트) | 간접 — 창이 커져도 E1이 살아있으면 규칙은 유지된다 |
| E10 | 하네스 버전 | Claude Code 2.1.226 | §4의 파일 경로·훅 이벤트 이름 |
| E11 | **다른 세션이 내 세션에 턴을 열 수 있나** (크로스세션 메시징) | 2.1.224+ **기본 ON**. `crossSessionInbound: "refuse"`로 막아둠 | E1·E3·R6·R13 — 막지 않으면 이것들이 **사람 없이** 우회된다 |

**E1·E2가 이 하네스의 축이다.** 컨텍스트가 "쌓여도 공짜"가 되거나 하네스가 죽은 구간을 자동 축출하면
R1·R2·R4·R5·R6·R7이 **한꺼번에** 불필요해진다. 그 경우 남는 건 R9·R10·R11(품질 규칙)뿐이다.
리뷰의 첫 질문은 그래서 "E1·E2가 아직 참인가"여야 한다.

**E11은 성격이 다르다.** E1~E10은 "하네스가 이렇게 동작한다"는 관찰이지만, E11은 **다른 프로세스가
내 세션의 전제를 깨뜨릴 수 있는가**를 묻는다. 이 하네스의 개입은 전부 "턴은 사람이 연다"를 암묵적으로
깔고 있다 — R6은 사람이 돌아올 때 가드하고, R13은 턴이 끝날 때 깨운다. 피어가 턴을 열 수 있으면
그 전제가 세션 밖에서 무너진다. 그래서 규칙을 하나 더 만드는 대신 **채널 자체를 닫았다**(§7-A).

## 2. 실제 파이프라인

```
요구사항
   │
   ├─(A) 기능 개발 ─────────────────────────────────────────────
   │     brainstorming 스킬로 인터뷰 → 스펙 저장
   │        └ 훅 plan-session-boundary-guard 발화 (ctx ≥120k)
   │     ── 세션 경계 ① /clear ──
   │     writing-plans → docs/<plandir>/plans/<name>/ 에 분할 저장
   │        00-overview.md (≤400행, 오케스트레이터가 읽는 유일한 파일)
   │        task-N.md      (구현자가 읽는 유일한 파일)
   │        └ 훅 plan-saved-session-boundary 발화 → 모드 1개 추천 + 자기완결성 4항목 점검
   │     ── 세션 경계 ② /exit → claude --effort X --model Y ──   ★ 유일한 강제 경계
   │     구현 (모드 ①/②a/②b/③ — §5)
   │        └ 훅 sdd-kickoff-guard 발화 → 플랜 통째 Read 금지
   │     plan-reviewer (레이어별 배치 1회, 같은 세션에서 스폰 가능)
   │     PR → pr-demo-video 스킬
   │
   ├─(B) UI·디자인 ─── show-design-sample 스킬 (브라우저 없이 샘플 URL 전달, N<=3은 빌더 1개·N>=4 또는 명시적 병렬 요청은 시안별 빌더, PR은 범위 밖)
   ├─(C) 디버깅 ────── systematic-debugging 스킬 (재현 절차를 산출물로)
   └─(D) 소규모 수정 ─ 위 전부 생략. 플랜 없이 바로. 훅은 발화 조건 미달로 조용함
```

**세션 경계는 ②만 강제다**(훅이 문구를 주입). ①은 소프트 주입이고, (D)에는 아무것도 안 걸린다.
이건 의도된 비대칭이다 — 실측에서 비용이 지배적인 구간이 "플래닝 잔재를 안고 구현하는 세션"이었다.

**상시 배경 규율**(파이프라인 어디서나): R3(서브에이전트 sonnet 기본) · R4(스크린샷 위임) ·
R5(탐색 위임) · R6(자리비움 핸드오프) · R12(stale 브랜치 경고).

## 3. 규칙 카탈로그

각 규칙: **기전**(무엇이 강제하는가) / **근거**(측정) / **대가** / **무효화 조건**.
근거의 상세는 `home/HARNESS-LOG.md` 해당 번호에 있다.

---

### R1 — 플랜 저장 후 세션 경계

**기전** `plan-saved-session-boundary.sh` (PostToolUse:Write). `docs/(superpowers|woobin_plan)/plans/*.md`
저장을 감지 → `/exit` 후 `claude --effort <모드> --model <모드>` 재런치 지시 + 자기완결성 4항목 점검 요구.
프로젝트 `CLAUDE.md`에 같은 절이 있다(이중 소유 — §9-1 참조).

**근거** 2026-07-29, 14일 전수, 구현 세션 18개. 구현 세션은 중앙값 **200k**를 물려받고 시작(최대 414k).
실행에 안 쓰이는 플래닝 잔재 ~155k를 이후 평균 95요청이 캐시 리드로 재청구 → 구현 단계 캐시 비용의
**44%** ($107.28/$242.65, 총지출의 ~9%). [HARNESS-LOG #5]

**대가** 사람이 세션을 한 번 끊어야 한다. 그리고 플랜이 자기완결적이지 않으면 새 세션이 되묻느라
절약분이 날아간다 — 그래서 경계를 넘기 **전에** 4항목 점검을 시킨다.

**무효화 조건** — 다음 중 하나라도 참이면 지워라
- E1이 거짓(캐시 리드 재청구가 없거나 무료)
- E2가 거짓(하네스가 컨텍스트의 죽은 구간을 자동 축출)
- 하네스가 세션 재시작 없이 컨텍스트를 선택적으로 리셋하는 수단을 제공
- **compaction이 무손실이 됨** — 이 규칙의 정체는 "compaction이 할 일을 미리, 정보 손실 없이 하는 것"이다.
  compaction이 잃는 게 없어지면 규칙의 존재 이유가 사라진다

### R2 — 플랜 분할 저장 (00-overview + task-N)

**기전** 같은 훅. 500행(`PLAN_SPLIT_MIN_LINES`) 초과 플랜은 `00-overview.md`(≤400행/15,000자) +
`task-N.md`로 쪼개고 원본은 스텁으로 교체. 이미 존재하는 단일 파일 플랜은 `sdd-kickoff-guard.sh`가
킥오프 시점에 "통째로 Read 금지, 목차·제약만" 결정론적 명령으로 커버.

**근거** 2026-07-30. R1 경계가 잘 작동했는데도 구현 세션 2개가 $52.64. 재시작 floor가 가정한 45k가
아니라 **93~122k**였고 최대 항목이 **플랜 통독 48k tok**(1,650행/74KB, Read 2회). floor는 오케스트레이터의
**매 요청**에 재청구된다(`ec809b30`: 158요청 × 141k = 22.8M = $11.39). 분할 후 재측정 **46k** ✅. [#6]

**여기서 나온 원칙** — "부분만 읽어라"는 소프트 지시로는 못 막는다. **읽을 파일 자체를 작게 만들어야 한다.**
이건 R2 하나를 넘어 이 하네스 전체의 설계 규율이다(§6-2).

**대가** 플랜 작성 세션이 파일을 여러 개 써야 하고, 태스크 간 참조가 파일 경로로 늘어진다.

**무효화 조건**
- 오케스트레이터가 큰 문서를 **부분 검색(retrieval)** 으로 읽을 수 있게 됨 — 읽은 만큼만 컨텍스트에 남는 구조
- 파일 Read가 컨텍스트에 원문으로 누적되지 않고 요약/포인터로 유지됨
- E2가 거짓

### R3 — 서브에이전트 model 기본값 sonnet

**기전** `subagent-model-default.sh` (PreToolUse:Agent|Task). `updatedInput`으로 **미지정일 때만** 주입.
존중: 호출에 model이 이미 있음 / 에이전트 정의에 model frontmatter 있음 / 플러그인 네임스페이스 타입(`codex:…`).

**근거** 2026-07-30. 메인이 opus인 상태에서 model 없이 스폰된 general-purpose 에이전트들이 opus로 돌아
하루 **$25.30**. 재측정 8/3 서브에이전트가 13개 전량 sonnet, opus 서브 **0건** ✅. [#8]

**기각한 대안** `CLAUDE_CODE_SUBAGENT_MODEL` 환경변수. 우선순위가 최상위라 Agent 호출의 명시적 `model`
인자와 에이전트 정의 frontmatter까지 **덮어쓴다**(2.1.220 바이너리 확인 — env가 있으면 tool/frontmatter
값을 버리고 telemetry에 `override_dropped` 기록). "최종 리뷰는 opus" 같은 의도적 승격이 조용히 깨진다.
→ **§6-5의 규율이 여기서 나왔다: env 전역 override보다 PreToolUse 조건부 주입.**

**대가** 정말 opus가 필요한 서브에이전트는 호출부나 정의에 명시해야 한다(모드 ③이 그 경우).

**무효화 조건**
- E5가 거짓(하네스 기본값이 inherit이 아님, 또는 Agent 툴이 model을 필수 인자로 요구)
- E6이 거짓(티어 간 가격차 소멸)
- 하네스가 태스크 난이도로 모델을 자동 라우팅

### R4 — 화면 검증은 `screenshot-verifier`에 위임

**기전** 프로젝트 `CLAUDE.md` 절 + `screenshot-verifier` 에이전트(sonnet, effort low, playwright 툴 보유).
훅 없음 — 소프트 규칙.

**근거** 2026-07-27. 스크린샷을 쓴 세션 3개가 그날 지출의 **63%**($63.15/$100.28). `089bf859`는 이미지
5장을 안은 채 223요청을 돌아 단독 $36.24. 재측정 8/3 메인 루프 이미지 유입 **0건**, big_results 103건→5건.
**하네스에서 가장 크게 개선된 항목.** [#2]

**⚠️ 근거 정정 이력** 최초 근거는 base64 글자수 기반이라 장당 비용을 50~100배 과장했다. 실제는 픽셀
기준((w×h)/750). 규칙은 유지하되 "비용을 이유로 다른 규율보다 앞세우지 않는다"로 격을 낮췄다. [#4]

**핵심 설계** — **예외를 명시한 게 규칙 성공의 원인이다.** "사용자에게 보여줄 데모 GIF Read는 위임하지
않는다." 이게 없으면 사용자가 볼 GIF까지 서브에이전트로 보내고 "판정: PASS"만 돌아오는 사고가 난다.

**대가** 왕복 1회. 그리고 판정이 텍스트라 미묘한 시각 판단은 손실된다.

**무효화 조건**
- 이미지가 컨텍스트에 상주하지 않고 참조로 유지됨
- E2가 거짓
- 멀티모달 입력 과금이 사라짐 **AND** 컨텍스트 점유도 사라짐 (둘 다여야 한다 — 점유만으로도 E1이 물린다)

### R5 — 코드 탐색은 `Explore`에 위임 (예외 3종)

**기전** 프로젝트 `CLAUDE.md` 절 + `Explore` 에이전트(haiku, effort low, 리포트 20줄 상한).
훅 없음 — **의도적으로.**

**근거** 2026-08-03~05 pholex 전수. 메인 직접 탐색 **261회**(Read 157 + Bash grep/find/sed 104) 대
`Explore` 위임 **1회**. `Grep`/`Glob` 툴은 0회 — 전부 Bash로 나간다(탐색 훅을 만든다면 이게 함정).
탐색분 캐시 재청구 누적 **$7.67**/4세션, 최대 `94aff112` **$5.57**(탐색 73k를 안고 268요청).
`Explore` 1회 실원가는 haiku 기준 **$0.295**. [#15]

**핵심 판단 — 위임이 항상 이득은 아니다.** 유일한 위임 사례는 세션이 직후 종료돼 **사실상 본전**이었다
($0.295 써서 ~$0.3 절약). 이득은 "탐색 이후 그 세션이 얼마나 더 도느냐"에 정비례한다.
그래서 예외 3종을 규칙과 **같은 급으로** 박았다: ① 3파일 이하로 끝나거나 턴이 곧 끝남
② 편집 루프 중 검증(테스트·빌드·방금 고친 파일 재확인) ③ 스타일을 원문 그대로 모방해야 할 때.

**왜 훅이 아닌가** 탐색과 검증을 **셸 문자열로 구분할 수 없다.** `sed -n '480,500p' Panel.tsx`는
방금 고친 파일 재확인(검증)인데 어떤 DISCOVER 정규식에도 걸린다. 오탐 = 편집 루프 방해라 대가가 크다.

**⚠️ 플랜 모드는 대안이 아니다** `EnterPlanMode` 툴 설명이 *"Thoroughly explore the codebase using
Glob, Grep, and Read"* — 메인이 직접 훑으라고 **지시**한다. 로컬 확인도 일치(유일 사용 세션에서 플랜 모드
중 Read×8 + Bash×7, 위임 0). "플랜 모드가 탐색을 자동 위임한다"는 웹 서술은 **틀렸다.**

**무효화 조건**
- 플랜 모드나 메인 루프가 탐색을 실제로 위임하도록 바뀜 (툴 설명 원문을 다시 확인해라)
- 탐색 결과가 컨텍스트에 원문으로 남지 않음
- 서브에이전트 왕복 지연이 커져 예외 3종이 규칙을 삼킴 → 그러면 규칙과 예외를 뒤집어야 한다

### R6 — 자리비움 자동 핸드오프

**기전** `idle-handoff-stop.sh` (Stop, asyncRewake) — 턴 종료 후 백그라운드 대기, 50분(`IDLE_HANDOFF_DELAY`)
무활동이면 `exit 2`로 모델을 깨워 **캐시가 살아있을 때** 핸드오프 문서를 쓰게 한다.
짝: `idle-return-guard.sh` (UserPromptSubmit) — 65분(`IDLE_GUARD_THRESHOLD`) 넘은 세션의 프롬프트를 1회 차단.
실경과가 59분(`IDLE_HANDOFF_MAXGAP`)을 넘겼으면(잠자기 등) "이 세션 이어가지 말고 새 세션으로" 버전을 주입.

**근거** 1시간 넘게 비우면 캐시 TTL 만료 → 복귀 첫 프롬프트 한 줄이 전체 컨텍스트를 재캐싱.
재측정 ttl1h 낭비 7/30 $17.99 → 8/3 **$10.64** ✅. [#1]

**사고 이력(설계에 박혀 있음)** 재주입 방지를 마커 파일로 했더니 rewake 주입 자체가 UserPromptSubmit
훅을 태우고 복귀 가드가 그 마커를 지우는 **레이스로 50분 주기 무한 루프**가 실제 발생했다.
→ 마커 대신 **transcript 파일 mtime 신선도**로 판정. **훅끼리 같은 상태 파일을 쓰면 순서 의존이 생긴다**는
교훈이 여기서 나왔고, `/close-session`을 별도 훅으로 빼지 않고 `idle-return-guard.sh` 안에 둔 이유도 같다.

**무효화 조건**
- E3 변경 — TTL이 자리비움 시간보다 길어지거나 캐시가 영속화되면 **이 규칙은 통째로 불필요하다**
- 하네스가 세션 재개 시 컨텍스트를 자동 복원(재캐싱 비용 없이)
- 임계값 3개(50/59/65분)는 TTL 1시간에 맞춘 값이다. TTL이 바뀌면 **규칙 유지 여부와 별개로 값부터 재계산**해라

### R7 — effort·model은 런치 플래그로 고정

**기전** `plan-exec-modes.md` 공통 규칙. `claude --effort <level> --model <model>`.
`/effort`는 쓰지 않는다 — interactive 세션에서 `effortLevel`에 **영구 저장**되어 되돌리기를 사람이
기억해야 하고, startup에 적용되지 않는 미해결 버그가 있다(anthropics/claude-code#45453).

**근거** E7 — effort 값이 렌더된 프롬프트에 들어가므로 세션 중 변경은 캐시 프리픽스를 통째로 무효화한다.
그리고 낮은 effort는 툴 호출을 병합·감소시킨다 → **턴 수를 직접 제어하는 게 effort다.**
비용을 움직이는 건 에이전트 수가 아니라 에이전트당 턴 수라는 외부 실측과 맞물린다. [#16]

**기각한 대안** 프로젝트 레벨 `effortLevel` 설정. 플래닝과 구현이 **같은 레포**에 살면서 서로 다른
effort를 원하기 때문에 레포 단위로는 못 나눈다.

**무효화 조건**
- E7이 거짓(effort가 프리픽스에 안 들어감) → 세션 중 변경 자유
- 하네스가 턴 단위로 effort를 자동 조절
- #45453이 수정되고 `/effort`가 세션 스코프가 됨 → `/effort`로 되돌아가도 된다

### R9 — 구현자에게 검증을 지시하지 않는다

### R11 — 리뷰는 코드를 쓰지 않은 컨텍스트에서

**무효화 조건**

- 서브에이전트가 부모 컨텍스트를 상속하게 됨 → **분리 조건이 깨지므로 진짜 세션 경계가 필요해진다**(규칙 강화 방향)

고치면 검사기를 돌려 결과를 additionalContext로 주입한다. 세션 1회, 차단하지 않는다.

**근거** 2026-08-10. `CLAUDE.md`의 "고칠 때 같이 고쳐야 하는 것"은 문서 4종을 **이미 명시하고 있었는데**,
R13 플랜을 쓰는 과정에서 `docs/workflow.html`이 빠졌고 사용자가 물어봐서 발견됐다. 같은 시점에
이 문서의 스킬 개수가 41개(실제 42개)로 이미 갈라져 있었다 — **산문 체크리스트가 이미 두 번 실패한 상태**였다.
R12(`stop-warning-ack-guard.sh`)가 만든 패턴 — "프롬프트로 부탁이 아니라 실제로 검사하는 결정론적 게이트" —
를 문서 동기화에 적용한 것이다(R12 무효화 조건의 "이 패턴은 다른 훅에도 적용 가능한데 안 쓰고 있다"가 이걸로 해소된다).

**설계 핵심** 실패(✗)와 경고(⚠)를 나눈다. 훅을 **추가**하면 사람용 요약의 서술이 바뀌므로
`workflow.html` 누락은 실패, 훅 **내용만** 수정하면 경고다. 모든 수정에 `workflow.html`을 요구하면
오탐이 쌓여 무시당하고, 그게 산문 규칙이 죽은 것과 같은 경로다.

**대가** 서식이 바뀌면 검사기의 정규식도 같이 고쳐야 한다(문구를 못 찾으면 ⚠로 알린다).
그리고 검사기 자체가 새로운 소유자다 — 개수 문구의 서식을 바꿀 때 여기도 봐야 한다.

**무효화 조건**
- 개수·인벤토리 문구가 문서에서 사라짐(자동 생성으로 바뀜) → 검사기의 해당 검사만 제거
- CI가 같은 검사를 돌리게 됨 → PostToolUse 짝은 중복이므로 제거하고 스크립트만 남긴다
- 재측정에서 ⚠ 오탐이 잦아 사용자가 무시하기 시작함 → 경고 항목을 줄이거나 실패로 올린다

### R15 — 레이어 경계 커밋 + 리뷰 후 push, draft PR이 회복 진입점

**기전** 훅이 아니라 **절차**다. 실행 절차의 단일 소유자는 `woobin-harness/plan-exec-modes.md`의
"중단 대비" 소절이고, 여기에는 근거·대가·무효화 조건만 적는다(§6-6 — 절차를 두 곳에 쓰지 않는다).
요지: 구현 시작 시 `plan/<plan-name>` 브랜치를 만들고 **플랜 문서를 첫 커밋**으로 올려
**draft PR**을 연다. 레이어가 끝나면 **커밋 → 리뷰 → (수정) → push** 순서로
진행하고, push할 때 그 레이어에서 발견한 것을 PR 코멘트에 5행 이내로 남긴다.
**마지막 레이어를 push하면 `gh pr ready`로 draft를 벗기고**, 머지는 **squash**로 한다.

**근거** 관측된 실패는 컨텍스트 성장이 아니라 **사용량 하드 컷**이다. R13은 Stop 훅이라 턴이 끝날 때만
발화하므로, 사용량이 소진돼 세션이 즉시 끊기는 경우를 **구조적으로 못 덮는다.** 그리고 컷 시점에는
모델이 아무 도구도 쓸 수 없으므로 방어는 조건부 발화가 아니라 **미리 배치**돼 있어야 한다.
사전 경고도 만들 수 없다 — `statusline/ctx-warn-statusline.sh`는 컨텍스트만 세고 훅 입력에
사용량 잔량이 없다(2026-08-10 확인). 그래서 이 절차는 조건부가 아니라 **무조건**이다.

**설계 핵심 — 하드 컷은 파일을 지우지 않는다.** 워킹 트리는 디스크에 남는다. 잃는 것은 코드가 아니라
**"어디까지 했는지"라는 기록**이다. 따라서 커밋의 역할은 보존이 아니라 **라벨링**이고, 라벨링은
레이어 해상도로 충분하다(태스크 단위 커밋은 §7-A에서 기각).
그리고 R13의 핸드오프 문서는 `~/.claude/idle-handoffs/<session_id>.md`에 저장되므로
**하드 컷 뒤에는 세션 id를 몰라 찾을 수 없다.** draft PR은 `gh pr list --state open --draft`로
사전지식 0에서 찾히므로, PR의 직무는 백업이 아니라 **회복 진입점**이다.

**불변식** 열린 **draft** 플랜 PR은 **워크트리당 1개.** 깨지면 "어느 PR이 살아있는 건지"를 목록만 보고
판정할 수 없어져 진입점의 값이 사라진다. 모드 ①은 트랙마다 워크트리이므로 트랙당 1개로 자연히 성립한다.

**상태는 draft 하나다 — 라벨을 쓰지 않는다(issue #3).** 초기 설계는 `plan-wip` 라벨을 썼다. 소비처는
둘(Layer 0 킥오프의 진행 중 플랜 검사, `stale-branch-guard.sh`의 하향 판단)이고 둘 다 `--state open`
필터라 머지 시점엔 자연히 빠졌지만, 그 논증은 **ready = 즉시 머지**를 전제한다. ready인 채로 승인·CI를
기다리는 창이 열리면 그 사이 다른 세션이 이 PR을 "아직 진행 중"으로 오판해 위 불변식에 막힌다.
창을 닫는 수단은 두 검사에 **`--draft`를 얹는 것**이고, 그러고 나면 라벨이 나르던 정보가 하나도 안 남는다 —
"플랜 PR임"은 R15가 이미 강제하는 `plan/` 브랜치 접두어가, "구현 중"은 draft가 나른다.
**파생 가능한 중복 상태를 손으로 동기화하는 것**이 이 레포가 반복해서 데인 실패 모드라(§6-6),
라벨을 "언제 뗄지" 정하는 대신 라벨 자체를 없앴다. 상태를 뒤집는 명령은 `gh pr ready` 하나뿐이다.

**규칙과 권장의 구분** `--squash` 머지는 **규칙**이다 — 레이어 커밋은 개별로 테스트를 통과하지 않을 수
있어, merge commit으로 들어가면 main의 `git bisect`가 못 믿을 것이 된다. 머지 전 플랜 디렉터리 삭제는
**권장**이다 — 잊어도 피해가 main 트리의 디렉터리 하나이고 되돌릴 수 있으며, 디렉터리 이름의 날짜
접두어와 `plans/` 경로가 이미 "현재 설계가 아님"을 표시한다.

**대가**
- **버리기가 되돌리기로 바뀐다.** 레이어당 커밋 1개면 `reset --hard HEAD~1`이라 `checkout .`과 비슷하지만,
  push된 뒤에 틀린 걸 알면 force-push가 된다. 이 교환의 판정은 **하드 컷 빈도 vs 방향 오류 빈도**이고
  아직 세지 않았다(§8 O14).
- **머신 유실 방어는 없다.** 원격은 리뷰된 레이어만 갖는다. 확인된 실패가 같은 머신의 사용량 컷이라
  의도한 축소다 — "push했으니 백업됐다"고 읽지 마라.
- **R13의 행동 유인을 약화시킬 수 있다.** 끊겨도 안 아프면 `/clear`를 미루게 된다. R13 무효화 조건의
  "핸드오프 문서가 만들어졌는데도 `/clear`하지 않는 비율"이 이미 그 감시 항목이다 — 재측정에서 그 비율이
  오르면 원인 후보로 이 규칙을 먼저 보라.
- **`gh` 인증에 의존한다.** graceful degrade를 두지 않는다 — 모델 호출 자체가 네트워크라
  "오프라인 구현"은 존재하지 않는 시나리오다. 원격이 없는 레포에서는 이 규칙 전체가 비적용이다.
- **ready 후 머지 전 세션에서는 R12 경고가 강한 문구로 돌아온다.** 하향 분기가 draft에 매달려 있어서다.
  방향이 fail-safe(경고가 세지는 쪽)라 감수했다 — 다만 그 창에서 "새 워크트리를 만들까요"를 묻는 건
  실제 상황(머지 직전 rebase 확인)과 어긋난다. 성가심이 관측되면 하향 조건을 `--state open` PR 존재로
  넓히는 게 다음 수단이다(§8 O17).
- **draft 하나에 두 뜻이 실린다** — GitHub의 "리뷰 준비 안 됨"과 이 규칙의 "구현 중". 이 레포에선
  일치하지만, 리뷰 가능하되 구현이 안 끝난 상태를 표현해야 하면 신호를 하나 더 만들어야 한다.
- **플랜이 아닌 draft PR과 섞인다.** 구분자는 `plan/` 브랜치 접두어이고, 검사는 목록 출력을 보고
  판정한다(서버 사이드 필터가 아니다). 열린 PR이 상시 0~1개라는 E-전제 위에서만 싸다.

**무효화 조건**
- 하네스가 **사용량 잔량을 훅 입력에 노출** → 무조건 절차를 조건부 발화로 좁힌다(R13처럼 임계에서
  깨우는 형태가 더 싸다)
- 하드 컷 후 세션 resume이 무손실이 되거나, `Workflow`의 `resumeFromRunId`를 실제로 쓰기 시작함
  → 폐기. §7-B의 "손으로 만든 모드는 중단 시 재개 수단이 없다"가 이 규칙의 존재 이유다
- 재측정에서 **하드 컷 중단 건수 < 방향 오류로 되돌린 건수** → 커밋 절차만 남기고 PR 기계를 버린다
- **열린 PR이 상시 여러 개인 레포로 이 규칙을 옮김** → `plan/` 접두어를 눈으로 거르는 게 안 통한다.
  그때 비로소 라벨이 값을 갖는다(서버 사이드 필터). 지금 없앤 이유가 사라지는 지점이다
- **draft가 "구현 중"과 어긋나기 시작함**(구현 중인데 리뷰를 받으려 ready로 올리는 일이 생김)
  → 신호를 분리해야 한다. draft에 두 뜻을 실은 대가가 실현된 것이다
- 소프트 절차가 지켜지지 않는 것이 관측됨 → §6-2대로 구조를 바꾼다(레이어 경계에서 더러운 트리를
  검사하는 훅). **먼저 훅을 만들지 않는다** — R13도 경고 → 실패 관측 → 훅 순서였다

## 5. 구현 모드

전문은 Claude Code용 `woobin-harness/plan-exec-modes.md`와 Codex용 `woobin-harness/plan-exec-modes-codex.md`. 공유 `writing-plans` 스킬이 호스트 대응본에서 **1개를 추천**한다 —
추천 근거는 overview의 순서 의존성이고, 그 판단은 **플랜을 방금 쓴 세션만 싸게 할 수 있다.**
아래 표는 Claude Code 런치 값이며, Codex 대응은 각각 `gpt-5.6-terra/medium`, `gpt-5.6/medium`, `gpt-5.6/xhigh`를 쓴다.

| 모드 | 런치 | 성립 조건 | 위임 |
|------|------|-----------|------|
| ① 속도 | `--effort xhigh --model sonnet` | 파일을 공유하지 않는 트랙 2개 이상. 트랙 1개면 ②보다 비싸기만 하다 | 트랙 단위 worktree, **순차 스폰** |
| ②a 절약 | `--effort medium --model sonnet` | 의존 체인. **대부분의 플랜** | 없음. 레이어마다 `/clear` |
| ②b 절약·무인 | `--effort medium --model sonnet` | 레이어 3개 이상이거나 자리를 비울 때 | 레이어마다 `plan-implementer` 순차 |
| ③ 최고품질 | `--effort xhigh --model opus` | 되돌리기 비싼 것 — DB 마이그레이션, prod 배포, 자동 게이트가 못 잡는 UI | 리뷰어 3개(렌즈 분리), 순차 |

**②a vs ②b는 "버리느냐 복제하느냐"뿐이다.** 둘 다 컨텍스트 성장을 막는다. ②a는 컨텍스트를 버려서
추가 비용 0이지만 레이어마다 사람 입력이 필요하고, ②b는 레이어당 프리픽스(38~88k)를 지불하는 대신
자리를 안 지켜도 된다.

**medium이 품질을 유지하는 근거**: Sonnet 5 @ medium ≈ Sonnet 4.6 @ high. 그리고 *"at low and medium,
the model scopes its work to what was asked rather than going above and beyond"* — 완결적 `task-N.md`
실행에서는 이게 **금도금 방지**로 작동한다. 얕은 추론이 보이면 프롬프트로 우회하지 말고 effort를 올린다
(단 세션 중간이 아니라 다음 세션에서 — R7).

**③이 `max`를 안 쓰는 이유**: *"on some structured-output or less intelligence-sensitive tasks it can
lead to overthinking."* 플랜 실행이 그 부류다.

## 6. 설계 규율 (하네스 전체에 반복 적용된 메타 규칙)

리뷰 시 이 6개는 개별 규칙보다 **상위**로 취급해라. 규칙은 바뀌어도 이건 남을 가능성이 높다.

1. **소프트 개입 우선** — 차단은 세션 1회 + 재시도 통과. 오탐이 영구 장애가 되면 안 된다.
   *단 예외*: 오탐의 대가가 비대칭이면 뒤집는다. `close-session-cleanup.sh`는 차단이 아니라 **보존**이
   기본값이다 — 여기서 오탐은 "남의 세션 작업 삭제"(복구 불가)라 재시도 통과 경로를 두지 않았고,
   `git branch -D`를 안 쓰므로 **커밋 유실이 구조적으로 불가능**하다.
   같은 계산이 프로세스 정리에도 적용된다(2026-08-12): 정책을 못 정하면 **안 죽인다**.
   *단 그 보존 규칙에도 예외가 있다* — 판정을 **이름이 아니라 출처로** 할 수 있으면 보존을 건너뛴다.
   자동화 브라우저(`--remote-debugging-*`·임시 프로필)와 이 레포에서 뜬 compose 스택은
   날아갈 사용자 데이터가 없어서 오탐의 대가가 애초에 비대칭이 아니다. 여기에 이름 기반 keep을
   적용하면 목적 자체가 무력화된다 — 실제로 그렇게 짰다가 잡으려던 1.9GB를 통째로 살려뒀다.
2. **소프트 지시로 못 막는 건 구조를 바꾼다** — "부분만 읽어라"가 안 먹혀서 파일 자체를 쪼갰다(R2).
3. **효과는 다음 audit에서 재측정한다** — 처방만 남기면 재발한다. `token-waste-audit` 스킬이 그 도구.
4. **근거 수치와 규칙은 별개로 검증** — 근거가 틀려도 규칙이 맞을 수 있다(R4).
5. **env 전역 override보다 PreToolUse 조건부 주입** — 의도적 예외를 조용히 깨뜨리지 않는다(R3).
6. **같은 문장을 두 곳이 소유하지 않는다** — 실제 사고: 스킬에서 SDD 문구를 지웠는데 훅에 하드코딩된
   사본이 남아 없는 스킬을 5회 더 권했고, 사용자가 매번 손으로 지웠다. 지금은 모드 파일 하나만 참조하고,
   그 파일이 없으면 모드 단계를 **통째로 생략**한다. → §9-1에 이 규율의 **현재 위반 1건**이 있다.

### B. 1st-party와의 중복 — 아직 손으로 하는 것들

**2026-08-08 시점에 발견된 미사용/중복 레버.** 리뷰 시 여기부터 봐라 — 하네스가 발전하면
손으로 만든 쪽이 먼저 낡는다.

| 손으로 만든 것 | 1st-party 대응물 | 현재 판단 |
|---|---|---|
| 모드 ① (트랙 병렬 + worktree 격리) | `Workflow` 툴의 `parallel()` / `isolation: 'worktree'` | **거의 같은 모양.** Workflow는 오케스트레이션 스크립트 자체가 토큰 0이고 `schema`로 구조화 출력을 강제한다. 안 쓰는 이유는 "사용자가 요청하지 않으면 workflow를 쓰지 않는다"는 세션 규율뿐 — **기술적 이유가 아니다** |
| 모드 ②b (레이어 순차 위임) | `Workflow`의 `pipeline()` | pipeline은 stage 간 **배리어가 없어** 아이템별로 독립 진행한다. 레이어가 의존 체인이면 이점이 없지만, 트랙이 여럿이면 ②b보다 낫다 |
| 모드 ③ (리뷰어 3개 렌즈 분리) | Workflow의 adversarial verify / judge panel 패턴 | 같은 패턴을 문서가 이미 권한다 |

## 9. 알려진 내부 모순

**리뷰어가 "발견"하기 전에 미리 적는다.** 이미 아는 것이므로 여기 있는 걸 지적해도 새 정보가 아니다.
새 것을 찾아라.

1. **세션 경계 문구가 두 곳에서 갈린다.** 프로젝트 `CLAUDE.md`는 `/clear`를 안내하고("컨텍스트만
   리셋하므로 터미널·워크트리·MCP 연결은 유지된다"), 훅과 모드 파일은 `/exit` 후 `--effort` 플래그로
   **재런치**를 지시한다. R7 도입 시 훅만 고치고 CLAUDE.md를 안 고쳤다. **§6-6 규율의 현재 위반이다.**
   `/clear`로는 effort를 못 바꾸므로 훅 쪽이 옳다.
2. **`sdd-*` 파일명이 실체와 안 맞는다.** SDD(subagent-driven-development) 스킬은 설치돼 있지 않다.
   `sdd-kickoff-guard.sh`는 트리거를 스킬명 → 구현 의도 정규식으로 이미 교체했고 절약 근거는 스킬과
   무관하게 유효하다. 이름만 역사적 표기로 남았다. 개명하면 훅 배선(`hooks.json`)도 같이 고쳐야 한다.
3. **편집 가드가 [A]/[B] 두 모드인데 [A]는 죽어 있다**(O5). 한 파일에 산 코드와 죽은 코드가 섞여 있다.
4. **R4(스크린샷)의 근거가 이미 한 번 50~100배 틀렸다.** 규칙은 유지가 옳았지만, 이 하네스에서
   **근거 검증이 가장 약했던 지점**이라는 기록으로 남긴다.
