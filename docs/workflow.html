새 작업은 이렇게 굴린다

기능 개발이든 리팩터든, 한 세션에서 설계를 스펙 파일 한 장으로 굳히고 리뷰를 받은 뒤 — 딱 한 번 세션을 끊고 — 새 세션에서 스펙만 쥐고 구현한다. 품질을 사는 레버는 계획서가 아니라 코드를 쓰지 않은 눈의 리뷰 2회다.

01전체 흐름

세션 경계는 스펙 리뷰 직후 /clear 딱 한 번이다. 스펙 파일 하나가 설계 → 구현 → 리뷰를 꿰는 유일한 산출물이다.

  • 진입 kick-off

    외울 트리거는 이것 하나다. /kick-off가 레포 상태를 보고 어느 단계부터 시작할지 정하고, 아래 분기 중 하나로 넘긴다. 상태는 .claude/kickoff.local.md에 남아 다음 세션이 이어받는다.

    사람만 부를 수 있게 막아뒀다(disable-model-invocation) — 모델이 알아서 켜는 프론트도어는 비슷한 스킬에 밀려 안 켜진다. 실제로 brainstorming이 3일 246세션에서 발동 0회로 삭제됐다. 난이도는 판정하지 않는다: /kick-off를 쳤다는 것 자체가 사용자의 판정이다.

  • 인터뷰 interview

    스펙 초안이 먼저다. 사실을 조사해 한 화면짜리 스펙을 내고, 정말 미결인 빈칸만 선택지로 묻는다. 매 라운드 결정 원장을 갱신한다.

    방향이 뒤집혀 있다 — 사용자가 추상적 질문에 답하는 게 아니라 구체적 초안에서 틀린 곳을 짚는다. 실측 27건에서 사용자는 대개 한두 번 답하고 다음 일로 넘어갔고, 마무리 assumptions 블록은 26세션 중 6번만 나왔다. 원장을 매 라운드 갱신하면 대화가 새도 그 시점까지가 남는다. 코드 조사는 Explore에 위임한다 — 인터뷰 세션의 컨텍스트를 설계 대화로만 채우기 위해서다.

  • 스펙 파일 저장 → 스펙 리뷰 spec-reviewer 같은 세션

    만들 작업이면 항상 파일로 떨군다 — docs/woobin_plan/specs/YYYY-MM-DD-<slug>-design.md. Goals · 결정 원장(기각한 대안 포함) · Acceptance criteria가 한 장에 들어간다. Acceptance criteria에는 기본 항목 둘이 붙는다: 자동 e2e로 증명하고 새 clone에서 재현, woobin-harness:code-reviewer 1사이클 findings를 PR 본문에 처리 결과와 함께 기록.

    저장하자마자 interview가 woobin-harness:spec-reviewer(opus · medium · 편집 불가)를 부른다. 모호함 · 검증 가능성 · 레포 사실과의 충돌 · 빈틈 · 범위 확장 · CLAUDE.md 준수를 보고 Status / Findings / Recommendations로 돌려준다. findings를 스펙에 반영한다. 킥오프 상태 파일이 있으면 이 순간 stage: impl로 바뀐다.

    구현 전에 리뷰를 한 번 두는 근거는 1차 실측이다 — 기본값 13건 · 충돌 6건 · 재검토 19건 같은 "빈틈 찾기" 이득이 구현 전 단계에서 나왔다. 계획서를 쓰는 것보다 스펙을 리뷰하는 쪽이 그 이득을 싸게 산다.

  • ◆ 필수 세션 경계

    스펙 리뷰까지 끝나면 /clear하고, 새 세션에는 스펙 파일 경로만 넘긴다. 설계 대화가 구현 구간의 매 요청에 캐시 리드로 재청구되는 걸 끊는 자리다. 훅은 없다 — 사람이 친다.

    /clear
# 첫 프롬프트 (한 줄)
docs/woobin_plan/specs/<date>-<slug>-design.md 스펙대로 구현해줘

  • 구현 시작 = 브랜치 + draft PR 회복 진입점

    첫 턴에 브랜치를 만들고 스펙 파일을 커밋해 push한 뒤 draft PR을 연다(제목·본문은 explain으로 "겪던 문제"부터 쓴다). 그 뒤로는 논리 단위로 커밋한다. draft는 "구현 중"이라는 뜻이고 라벨은 쓰지 않는다(중복 상태를 손으로 맞추게 된다). 절차 정본은 interview 스킬의 "구현 세션으로 넘기기" 절이다.

    겨누는 건 컨텍스트가 아니라 사용량 하드 컷이다. 그 순간엔 모델이 도구를 못 쓰니 방어가 미리 배치돼 있어야 한다. 하드 컷은 파일을 지우지 않는다 — 잃는 건 "어디까지 했는지"라는 기록이라 커밋은 보존이 아니라 라벨링이다. 핸드오프 문서는 세션 id로 저장돼 컷 뒤엔 못 찾지만, PR은 gh pr list --state open --draft로 찾힌다.

  • 구현 한 세션

    스펙을 읽고 한 세션이 직접 끝까지 구현한다. 레이어로 나누거나 구현자 서브에이전트에 넘기지 않는다. 모드 선택도 없다.

    세션 하나를 넘는 크기 · 병렬 트랙 · 마이그레이션용 분할 수단은 일부러 안 남겼다. 필요해지면 git 이력에서 복원한다(R23 무효화 조건 (a)).

  • 코드 리뷰 code-reviewer

    구현이 끝나면 woobin-harness:code-reviewer(opus · medium · 편집 불가)를 1사이클 띄운다. 같은 세션에서 띄워도 된다 — 서브에이전트는 부모 대화 컨텍스트를 물려받지 않는다. 축은 셋: 정확성 · Acceptance criteria 대조 · 레포 관례.

    diff 본문을 넘기지 않는다. 스펙 파일 경로 + origin/main..HEAD 범위만 주면 자기가 뜬다. finding마다 심각도·확신도가 달려 나오고, 받은 findings와 처리 결과를 PR 본문에 남긴다. 2차 실측에서 레이어별 리뷰가 놓친 결함(드래그 폭 키 공유)을 이 스펙 대조 리뷰가 잡았다.

  • e2e 증명 → ready explain

    Acceptance criteria대로 자동 e2e로 증명하고 새 clone에서 재현한다. 그다음 explain 스킬로 PR 제목·본문을 서사로 쓰고 gh pr ready로 draft를 벗긴다. 머지는 사람이 낸다.

    PR 제목·본문은 변경 파일 목록이 아니라 "사용자가 겪던 문제 → 어떻게 풀었나"다. 제목은 squash 머지 커밋 제목이 되므로 slug가 아니라 산문이다.

  • ◆ 자동 세션 경계 (300k)

    턴이 300k 컨텍스트를 넘겨 끝나면 ctx-handoff-stop.sh가 모델을 깨워 handoff 스킬로 핸드오프 문서를 ~/.claude/idle-handoffs/<sid>.md에 쓰게 한다. 그 뒤 /clear하고 그 문서를 읽고 이어가면 된다. 세션당 1회만 발화한다.

    계획된 경계는 위의 필수 /clear 하나뿐이지만, 이건 넘겼을 때 자동으로 생기는 경계다. 2026-08-10 7일 전수에서 300k를 넘긴 뒤에도 계속 돈 세션이 10건이었고 그 초과분만 $88.47이었다.

  • 마무리

    /close-session 으로 워크트리·브랜치 정리. 머지는 사람이 낸 뒤다.

    세션이 띄우고 안 내린 것도 같이 걷는다 — e2e·MCP 브라우저와 이 레포에서 뜬 compose 스택. 둘 다 이름이 아니라 출처로 고른다(Playwright가 띄운 Chrome도 프로세스 이름은 그냥 "Google Chrome" 이라 이름으로는 일상용과 구분이 안 된다). 직접 켜둔 GUI 앱은 ~/.claude/close-session-keep.conf 의 정책을 타고, 판정이 안 서면 안 끈다. 무엇이 왜 남았는지는 CLOSE_SESSION_DRY_RUN=1 로 본다.

02왜 계획서가 아니라 리뷰인가

2026-10-01까지는 스펙 다음에 분할 계획서를 쓰고, 모드를 골라 레이어별로 구현했다. 같은 작업을 두 경로로 두 번 돌려 비교했고(이슈 #41), 계획서 단계를 통째로 지웠다.

1차Godot M1 · 2026-09-28

자유 구현 $54 · 2시간 대 계획 경로 $95~100 · 4시간 20분. 품질은 코드 구조를 빼면 자유 구현이 앞섰다.

계획 경로가 건진 건 구현 전의 빈틈 찾기(기본값 13 · 충돌 6 · 재검토 19)였다 → 스펙 리뷰로 남겼다.

2차pholex 대시보드 · 2026-10-01

기존 코드베이스. 자유 구현 $9.8 · 18분 대 계획 경로 $24~27 · 56분. 블라인드 리뷰 점수는 계획 경로 8.5, 자유 구현 8.2.

자유 구현에 독립 리뷰 1사이클($3.4)을 더하자 계획 경로를 이겼다. 레이어별 리뷰가 놓친 결함을 스펙 대조 리뷰가 잡았다.

→지금 기본 경로기본

스펙 파일 → spec-reviewer → /clear → 한 세션 구현 → code-reviewer → e2e 증명 → ready.

계획 경로가 끌고 다니던 전용 에이전트 6종 · 훅 3종 · 모드 문서도 같이 지웠다. 문서 4종이 함께 움직여야 해서 한쪽만 고쳐 갈라지는 사고가 반복되던 자리다.

03늘 지키는 것

대부분 공식 문서 근거가 있다. 어기면 토큰만 늘고 품질은 그대로다.

✕ 구현 세션에 "검증해라" 금지

Opus 5는 시키지 않아도 자기 검증을 한다. 명시 지시와 legacy harness scaffolding은 over-verification을 부른다. 검증은 별도 컨텍스트(code-reviewer)와 자동 e2e의 몫.

✕ 리뷰에 "심각한 것만" 금지

모델이 리터럴하게 따라서 덜 보고한다. 전부 보고하게 하고 심각도·확신도로 랭킹은 나중에.

✓ effort는 시작할 때 정하고 고정

effort 값이 렌더된 프롬프트에 들어간다 — 세션 중간에 바꾸면 캐시 프리픽스가 통째로 무효화된다.

✓ 구현 세션에는 스펙 파일 경로만

설계 대화가 구현 세션에 올라가면 그 토큰을 이후 모든 요청이 캐시 리드로 다시 낸다. 스펙 파일 한 장이면 구현 세션이 알아야 할 것이 다 들어 있다.

✓ 커밋은 리뷰 전에

리뷰가 그 세션에서 토큰을 가장 많이 쓰는 단계라 하드 컷 확률이 가장 높다. 커밋을 리뷰 뒤로 미루면 작업 전체가 가장 위험한 순간에 무기록으로 노출된다. 커밋은 로컬이고 공짜다.

✓ 한국어는 output-style이 미리 잡는다

플러그인이 fluent-korean 출력 스타일을 나르고 settings.json의 outputStyle이 켠다. 조사·어미 생략과 명사구 종결을 출력 전에 막는 게 목적이다 — 서브에이전트에 한국어 프롬프트를 넘기는 구조라 품질 저하가 단계마다 누적된다. 훅은 쓰지 않는다. 대가는 토큰이고, 근거가 로컬 실측이 아닌 유일한 규칙이다(R16 · O18).

ℹ 확인이 필요하면 서브에이전트는 못 묻는다

AskUserQuestion은 모든 서브에이전트에서 제거된다. 그래서 위임하는 건 판정만 돌려주면 되는 일(탐색 · 화면 확인 · 리뷰)뿐이고, 구현과 스펙 작성은 사람과 대화하는 메인 세션이 직접 한다.

ℹ 서브에이전트 기본 모델은 opus

model을 안 적고 띄운 서브에이전트는 훅이 opus로 맞춘다(2026-10-01, 이전엔 sonnet). 비용보다 리뷰·탐색 품질을 골랐다. 싸게 돌릴 에이전트는 정의에 박아둔다 — Explore는 haiku, screenshot-verifier는 sonnet. 비용 영향은 아직 다시 재지 않았다.

ℹ 설치본 최신 여부

세션이 열릴 때 플러그인 설치본이 레포보다 뒤처졌는지 본다. 뒤처졌으면 갱신 절차를 알려준다 — 레포를 고쳐도 version을 안 올리면 설치본은 옛날 그대로 돈다.

메인 컨텍스트에 원문을 쌓지 않는 게 목적이다. 결론만 회수한다.

05더 밀어붙이고 싶을 때

기본 경로는 세션 하나에 들어가는 작업을 전제한다. 그보다 큰 일에만 해당하고, 둘 다 명시적으로 요청해야 발동한다.

수단무엇언제
Workflow 제어 흐름을 JS 스크립트로 고정한다. pipeline()·parallel()로 트랙·레이어를 돌리고, 스키마로 반환 형태를 강제하며, 중간에 끊겨도 이전 단계는 캐시에서 즉시 복구된다. 세션 하나를 넘는 작업을 트랙·단계로 나눠야 할 때. 분할 수단을 git 이력에서 손으로 되살리기 전에 이것부터 본다. 스크립트 자체는 토큰 0.
--effort ultracode xhigh 추론 + 작업마다 동적 워크플로를 짜게 하는 세션 설정. 되돌리기 비싼 작업(DB 마이그레이션, prod에 닿는 변경)을 한 세션에서 더 깊게 굴리고 싶을 때. 세션 전용이라 설정에 안 남는다.

06하지 말 것

전부 실제로 한 번씩 겪은 것들이다.

  • 스펙을 쓴 세션에서 그대로 구현 시작 설계 대화가 구현 구간의 매 요청에 캐시 리드로 재청구된다. 막아주는 훅은 없다 — 스펙 리뷰 뒤 /clear는 사람이 친다.
  • 리뷰 2회 중 하나 건너뛰기 품질을 산 건 계획서가 아니라 리뷰였다. 훅이 강제하지 않으므로(호출은 지시문) 건너뛰면 아무도 모른다. code-reviewer 결과는 PR 본문 ### 리뷰 절에 남겨 흔적을 만든다.
  • 세션 중간에 /effort 를 다시 치기 effort 값이 프롬프트에 들어가므로 중간에 바꾸면 그때까지의 캐시가 전부 날아간다. 게다가 settings.json에 영구 저장돼 되돌리기를 사람이 기억해야 한다.
  • "빠르게 하려고" 작업을 쪼개 서브에이전트 여러 개로 구현 의존이 있으면 이득이 0이고 프리픽스 비용만 붙는다. 게다가 서브에이전트는 확인을 못 물어서 애매한 곳에서 임의 판단하거나 멈춘다.
  • 탐색 결과·diff·테스트 출력을 메인에 그대로 쌓기 한 번 쌓이면 그 세션이 끝날 때까지 매 요청이 다시 낸다. 위임하고 결론만 받는다.
  • 스크린샷을 메인에서 Read 이미지 토큰은 픽셀 기준으로 붙고 누적된다. 단, 사용자에게 보여줄 GIF는 예외 — 그건 메인에서 띄워야 의미가 있다.
  • 경로·폴더명을 코드에 리터럴로 박기 이름을 바꾸는 순간 훅은 에러 없이 침묵하고 CI는 빨개진다. 훅은 PLAN_DOCS_DIRS 같은 env var로, 테스트 제외는 .no-doc-scan 같은 마커 파일로 판정한다.
