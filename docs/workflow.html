Claude Code · 개인 하네스

새 작업은 이렇게 굴린다

기능 개발이든 리팩터든, 한 세션에서 설계와 플랜까지 끝내고 — 딱 한 번 세션을 끊고 — 새 세션에서 플랜만 쥐고 구현한다. 속도와 품질을 사는 레버는 서브에이전트가 아니라 model · effort다.

01전체 흐름

세션 경계는 플랜 저장 직후 딱 한 번이다. 예전처럼 레이어마다 끊지 않는다.

  • 인터뷰 grill-me

    스펙 초안이 먼저다. 사실을 조사해 한 화면짜리 스펙을 내고, 정말 미결인 빈칸만 선택지로 묻는다. 매 라운드 결정 원장을 갱신한다.

    방향이 뒤집혀 있다 — 사용자가 추상적 질문에 답하는 게 아니라 구체적 초안에서 틀린 곳을 짚는다. 실측 27건에서 사용자는 대개 한두 번 답하고 다음 일로 넘어갔고, 마무리 assumptions 블록은 26세션 중 6번만 나왔다. 원장을 매 라운드 갱신하면 대화가 새도 그 시점까지가 남는다. 원장이 커지거나 이번 플랜보다 오래 살 설계면 docs/woobin_plan/specs/로 떨군다 — 결정 3~4개짜리면 플랜의 "기각한 대안" 절이 같은 일을 한다.

  • 플랜 작성 writing-plans 같은 세션

    코드 조사는 전부 Explore에 위임한다. 이게 인터뷰와 플랜을 한 세션에 둘 수 있는 유일한 조건이다.

    처음부터 분할해서 쓴다 — plans/YYYY-MM-DD-<slug>/00-overview.md(≤400행) + task-N.md. 기존 플랜 파일은 건드리지 않는다(append-only).

    플랜 진입 경계를 정당화하던 비용은 "대화가 앉아 있어서"가 아니라 "메인 루프의 grep·sed가 쌓여서"였다. 탐색을 위임하면 그 항이 사라진다.

  • 플랜 저장 → 훅이 3가지를 시킨다 자동

    ① 자기완결성 점검 — 경로 / 기각 대안 / 대화 참조 0건 / 완료 판정 명령

    ② 분할 — 스킬 없이 통짜로 저장됐고 500행을 넘으면 00-overview.md + task-N.md로 쪼개라고 지시한다. 이미 분할돼 있으면 00-overview.md 저장 때 1회만 발화하고 이 항목은 건너뛴다.

    ③ 모드 추천 — 근거는 overview의 "태스크 간 순서 의존성"

    지금 이 세션만 그 판단을 싸게 할 수 있어서 여기에 박아뒀다.

  • ◆ 필수 세션 경계

    이 세션을 종료하고 모드에 맞는 플래그로 다시 띄운다. /effort는 쓰지 않는다 — settings.json에 영구 저장돼서 되돌리기를 사람이 기억해야 한다.

    claude --effort medium --model sonnet
# 첫 프롬프트 (한 줄)
docs/woobin_plan/plans/<name> 플랜으로 구현 진행해줘 — 모드 ②b

  • 구현 시작 = 브랜치 + draft PR R15

    첫 턴에 plan/<name> 브랜치를 만들고 플랜 문서를 첫 커밋으로 올려 draft PR을 연다. 레이어가 끝날 때마다 커밋 → 리뷰 → push. 마지막 레이어를 push하면 gh pr ready로 draft를 벗긴다 — draft는 "구현 중"이지 "머지 전"이 아니다. 라벨은 쓰지 않는다(중복 상태를 손으로 맞추게 된다).

    겨누는 건 컨텍스트가 아니라 사용량 하드 컷이다. 그 순간엔 모델이 도구를 못 쓰니 방어가 미리 배치돼 있어야 한다. 하드 컷은 파일을 지우지 않는다 — 잃는 건 "어디까지 했는지"라는 기록이라 커밋은 보존이 아니라 라벨링이고 레이어 해상도로 충분하다. 핸드오프 문서는 세션 id로 저장돼 컷 뒤엔 못 찾지만, PR은 gh pr list --state open --draft로 찾힌다.

  • 구현 모드대로

    킥오프 가드가 "00-overview.md만 읽어라"를 자동 주입한다. task-N.md는 구현 직전에 하나씩, 또는 서브에이전트에 경로로만 넘긴다.

    effort는 세션 내내 고정. 얕은 추론이 보이면 프롬프트로 우회하지 말고 다음 세션에서 올린다.

  • 리뷰 plan-reviewer

    구현이 다 끝난 뒤 레이어별 배치 1회. 같은 세션에서 띄워도 된다 — 서브에이전트는 부모 대화 컨텍스트를 물려받지 않는다.

    diff 본문을 넘기지 않는다. task-N.md 경로 + main..HEAD 범위만 주면 자기가 뜬다. finding마다 심각도·확신도가 달려 나온다.

  • ◆ 자동 세션 경계 (300k)

    턴이 300k 컨텍스트를 넘겨 끝나면 ctx-handoff-stop.sh가 모델을 깨워 handoff 스킬로 핸드오프 문서를 ~/.claude/idle-handoffs/<sid>.md에 쓰게 한다. 그 뒤 /clear하고 그 문서를 읽고 이어가면 된다. 세션당 1회만 발화한다.

    계획된 경계는 위의 필수 하나뿐이지만, 이건 넘겼을 때 자동으로 생기는 경계다. 2026-08-10 7일 전수에서 300k를 넘긴 뒤에도 계속 돈 세션이 10건이었고 그 초과분만 $88.47이었다.

  • 마무리

    /close-session 으로 워크트리·브랜치 정리. effort 되돌리기는 필요 없다 — 런치 플래그는 그 세션에서만 살았다.

    세션이 띄우고 안 내린 것도 같이 걷는다 — e2e·MCP 브라우저와 이 레포에서 뜬 compose 스택. 둘 다 이름이 아니라 출처로 고른다(Playwright가 띄운 Chrome도 프로세스 이름은 그냥 "Google Chrome" 이라 이름으로는 일상용과 구분이 안 된다). 직접 켜둔 GUI 앱은 ~/.claude/close-session-keep.conf 의 정책을 타고, 판정이 안 서면 안 끈다. 무엇이 왜 남았는지는 CLOSE_SESSION_DRY_RUN=1 로 본다.

02어느 모드로 갈까

고르는 기준은 딱 하나 — 태스크들이 같은 파일을 건드리는가. 플랜을 쓴 세션이 추천해준다.

①속도

파일을 공유하지 않는 트랙이 2개 이상일 때만. 트랙이 1개면 ②보다 비싸기만 하다.

claude --effort xhigh --model sonnet

트랙 단위 worktree 병렬. 동시에 띄우지 않는다 — 첫 트랙이 응답한 뒤 다음.

②a절약 · 수동기본

의존성 체인이거나 같은 파일 공유. 확인 게이트가 잦을 때 이쪽.

claude --effort medium --model sonnet

서브에이전트 0. 레이어마다 /clear. 컨텍스트를 버리므로 추가 비용 0 — 대신 자리를 지켜야 한다.

②b절약 · 위임기본

같은 조건인데 레이어 3개 이상이거나 자리를 비울 때.

claude --effort medium --model sonnet

레이어당 plan-implementer 1개, 직렬. 컨텍스트를 복제하므로 레이어 수만큼 프리픽스를 산다 — 대신 끝까지 자동.

③최고 품질

되돌리기 비싼 작업 — DB 마이그레이션, 사내 prod에 닿는 변경, 자동 게이트가 못 잡는 UI.

claude --effort xhigh --model opus

본체는 구현이 아니라 렌즈를 나눈 리뷰어 3개. max는 쓰지 않는다 — 구조화된 작업에서 overthinking.

03어느 모드에서도 지키는 것

셋 다 공식 문서 근거가 있다. 어기면 토큰만 늘고 품질은 그대로다.

✕ 태스크 단위 팬아웃 금지

작은 태스크를 병렬로 쪼개면 순차 대비 토큰 2.6~5.9배이고 한 번도 더 빠르지 않았다. 위임은 레이어·트랙 단위로만.

✕ 구현자에게 "검증해라" 금지

Opus 5는 시키지 않아도 자기 검증을 한다. 명시 지시와 legacy harness scaffolding은 over-verification을 부른다. 검증은 별도 컨텍스트의 몫.

✕ 리뷰에 "심각한 것만" 금지

모델이 리터럴하게 따라서 덜 보고한다. 전부 보고하게 하고 심각도·확신도로 랭킹은 나중에.

✓ effort는 시작할 때 정하고 고정

effort 값이 렌더된 프롬프트에 들어간다 — 세션 중간에 바꾸면 캐시 프리픽스가 통째로 무효화된다.

✓ 오케스트레이터는 overview만

task-N.md 본문이 메인에 올라가면 그 토큰을 이후 모든 요청이 캐시 리드로 다시 낸다.

✓ 커밋은 리뷰 전, push는 리뷰 후

레이어 끝의 리뷰가 그 세션에서 토큰을 가장 많이 쓰는 단계라 하드 컷 확률이 가장 높다. 커밋을 리뷰 뒤로 미루면 레이어 전체가 가장 위험한 순간에 무기록으로 노출된다. 머지는 --squash — 레이어 커밋은 개별로 테스트를 통과하지 않을 수 있어 merge commit이면 git bisect가 못 믿을 것이 된다.

✓ 한국어는 output-style이 미리 잡는다

플러그인이 fluent-korean 출력 스타일을 나르고 settings.json의 outputStyle이 켠다. 조사·어미 생략과 명사구 종결을 출력 전에 막는 게 목적이다 — 서브에이전트에 한국어 프롬프트를 넘기는 구조라 품질 저하가 단계마다 누적된다. 훅은 쓰지 않는다. 대가는 토큰이고, 근거가 로컬 실측이 아닌 유일한 규칙이다(R16 · O18).

ℹ 확인이 필요하면 서브에이전트는 못 묻는다

AskUserQuestion은 모든 서브에이전트에서 제거된다. 그래서 plan-implementer는 게이트에서 멈추고 보고하고, 플랜 작성 자체는 절대 위임하지 않는다.

ℹ 설치본 최신 여부

세션이 열릴 때 플러그인 설치본이 레포보다 뒤처졌는지 본다. 뒤처졌으면 갱신 절차를 알려준다 — 레포를 고쳐도 version을 안 올리면 설치본은 옛날 그대로 돈다.

04무엇을 누구에게 위임하나

메인 컨텍스트에 원문을 쌓지 않는 게 목적이다. 결론만 회수한다.

상황보낼 곳돌려받는 것예외 — 직접 한다
코드가 어디 있나 / 어떻게 도나 Explore file:line 결론 파일 3개 이하 · 편집 루프 중 검증 · 스타일을 원문 그대로 따라 써야 할 때
화면이 제대로 나왔나 screenshot-verifier 판정 텍스트 사용자에게 보여줄 데모 GIF — 그건 메인에서 Read
제품 UI 방향·구현·리뷰·반복 실패 design-workflow 작업을 분류해 direction, system-evidence, implementation-contracts, review, evolution 중 필요한 모듈만 읽는다. DESIGN.md가 없어도 진행한다. 복수 시안 격리 프리뷰·공유가 필요할 때만 show-design-sample
레이어 하나 구현 (모드 ②b·①) plan-implementer 25행 요약 모드 ②a·③ — 메인 루프가 직접
구현 결과 검토 plan-reviewer 심각도·확신도 붙은 findings 고치는 건 항상 메인 몫 (리뷰어는 편집 권한 없음)

05더 밀어붙이고 싶을 때

모드 ①·③에만 해당한다. 둘 다 명시적으로 요청해야 발동한다.

수단무엇언제
Workflow 제어 흐름을 JS 스크립트로 고정한다. pipeline()·parallel()로 트랙·레이어를 돌리고, 스키마로 반환 형태를 강제하며, 중간에 끊겨도 이전 단계는 캐시에서 즉시 복구된다. 모드 ①의 트랙 병렬, 모드 ③의 렌즈 3분할. 스크립트 자체는 토큰 0.
--effort ultracode xhigh 추론 + 작업마다 동적 워크플로를 짜게 하는 세션 설정. 모드 ③을 손으로 조립하기 싫을 때. 세션 전용이라 설정에 안 남는다.

06하지 말 것

전부 실제로 한 번씩 겪은 것들이다.

  • 플랜 저장한 세션에서 그대로 구현 시작 설계 대화가 구현 구간의 매 요청에 캐시 리드로 재청구된다. 훅이 막아주지만, 훅이 안 뜨면 수동으로 지킨다.
  • 레이어마다 세션을 끊으려고 /effort 를 다시 치기 effort는 런치 플래그로 한 번만. 중간에 바꾸면 그때까지의 캐시가 전부 날아간다.
  • "빠르게 하려고" 태스크마다 서브에이전트 띄우기 의존이 있으면 이득이 0이고 프리픽스 비용만 붙는다. 게다가 서브에이전트는 확인을 못 물어서 게이트에서 임의 판단하거나 멈춘다.
  • 탐색 결과·diff·테스트 출력을 메인에 그대로 쌓기 한 번 쌓이면 그 세션이 끝날 때까지 매 요청이 다시 낸다. 위임하고 결론만 받는다.
  • 스크린샷을 메인에서 Read 이미지 토큰은 픽셀 기준으로 붙고 누적된다. 단, 사용자에게 보여줄 GIF는 예외 — 그건 메인에서 띄워야 의미가 있다.
  • 경로·폴더명을 코드에 리터럴로 박기 이름을 바꾸는 순간 훅은 에러 없이 침묵하고 CI는 빨개진다. 훅은 PLAN_DOCS_DIRS 같은 env var로, 테스트 제외는 .no-doc-scan 같은 마커 파일로 판정한다.

07Codex 호환 레이어

스킬은 하나, 런타임 계약만 분리한다.

  • 공통 스킬 20개 woobin-harness/skills/를 Claude Code와 Codex가 함께 읽는다.
  • Codex 훅 4개 플랜 킥오프, 문서 동기화, stale-branch 경고와 응답 검사만 연결한다. 비동기 idle handoff와 Claude transcript·모델명 의존 훅은 미연결이다.
  • Codex 에이전트 4개 플러그인 밖의 codex/agents/*.toml을 bootstrap-codex.sh가 설치한다.
  • 호스트별 구현 모드 Claude Code는 plan-exec-modes.md, Codex는 plan-exec-modes-codex.md가 모델·effort·에이전트 이름을 각각 소유한다.

모드 정본은 woobin-harness/plan-exec-modes.md(Claude Code)와 plan-exec-modes-codex.md(Codex)다 — 공통 선택 조건은 맞추되 호스트 고유 명령은 섞지 않는다. 공통 스킬과 훅 스크립트는 woobin-harness 플러그인이 나른다. 새 머신 셋업은 Claude Code가 bootstrap.sh, Codex가 bootstrap-codex.sh.
