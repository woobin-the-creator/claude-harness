# Design Workflow Dashboard Experiment 설계 명세

날짜: 2026-08-13  
상태: 사용자 승인 완료

## 1. 목적

PR #9의 새 `design-workflow`가 웹 대시보드 생성 품질을 실제로 개선하는지 탐색적으로 비교한다. 비교 조건은 다음 세 가지다.

- A: 디자인 스킬을 사용하지 않는 순수 모델
- B: `origin/main`에 있는 PR 이전 `design-rules`
- C: PR #9의 새 `design-workflow`

이번 실험이 특히 보고 싶은 차이는 생성 프롬프트에 공개하지 않는다.

- 입력받을 값의 길이와 성격을 고려한 폼 치수
- 팝오버 종료, 긴 선택 목록 탐색, 검색 위치, 저장·취소 같은 기본 UX 관행
- 긴 데이터, 테이블, 스크롤, overflow, 상태 표현의 견고성

한 조건당 한 번 생성하는 1차 실험으로 시작한다. 결과 차이가 불분명하거나 모델 편차로 보이면 같은 절차로 2차 샘플을 생성한다. 한 번의 결과를 일반적인 인과 증명으로 과장하지 않는다.

## 2. 실험 원칙

### 2.1 유일한 의도적 변수

세 조건은 같은 모델, 추론 수준, 구현 시간 예산, 공통 제품 명세, fixture 데이터, 런타임 의존성을 사용한다. 의도적으로 바꾸는 것은 디자인 스킬 조건뿐이다.

- A에는 디자인·웹 제작 관련 스킬을 읽거나 호출하지 말라는 실험 조건을 준다.
- B에는 `origin/main`에서 추출한 기존 `design-rules` 정본만 제공한다.
- C에는 PR #9의 `design-workflow` Router와 해당 route가 요구하는 reference만 제공한다.

각 생성기는 다른 생성기의 프롬프트, 코드, 화면, 평가표를 볼 수 없다. 생성 프롬프트에는 사용자의 디자인 불만, 기대 해법, 채점 항목, 조건 매핑을 넣지 않는다.

### 2.2 독립 컨텍스트

각 구현은 대화 이력을 상속하지 않는 새 컨텍스트에서 실행한다. 생성기에는 다음만 전달한다.

1. 공통 제품 brief
2. 공통 기능 계약
3. 공통 fixture와 타입
4. 자기 조건의 스킬 지침
5. 자기 소유 출력 디렉터리

생성기는 저장소의 이 명세, 평가 스크립트, 형제 variant 디렉터리, 다른 디자인 스킬을 읽지 않는다. 오케스트레이터는 각 작업에 파일 소유권을 명시하고, 형제 구현을 되돌리거나 수정하지 못하게 한다.

### 2.3 블라인드 공개

완성된 A/B/C는 평가 전에 순서를 무작위로 섞어 X/Y/Z로 노출한다. 랜덤 매핑은 생성 코드와 평가 화면에서 분리해 보관한다. 사용자가 블라인드 점수와 선호를 확정한 뒤에만 조건을 공개한다.

## 3. 제품 brief

제품은 한국어 데스크톱 웹 앱인 콜드체인 물류 관제 대시보드다. 사용자는 교대 근무 중인 물류 관제 담당자다. 핵심 과업은 다음과 같다.

- 진행 중인 운송과 이상 상태를 빠르게 파악한다.
- 여러 조건으로 운송을 좁히고 다수 건을 선택해 일괄 조치한다.
- 운송 상세, 센서 변화, 이전 조치 이력을 확인한다.
- 기사·차량·허브 배차 정보를 수정한다.
- 알림을 확인하고 처리 상태를 바꾼다.

제품명, 로고, 색상, typography, 레이아웃, 시각적 signature는 공통 프롬프트에서 정하지 않는다. 생성기는 추가 질문 없이 합리적인 제품 가정을 세우고 인터랙티브 목업을 완성한다. 백엔드, 인증, DB, API는 구현하지 않는다.

## 4. 공통 데이터 계약

fixture는 세 variant가 같은 파일 내용을 독립적으로 복사해 사용한다. 런타임에 형제 variant의 코드를 import하지 않는다.

### 4.1 데이터 규모

- 진행 중 운송 64건
- 기사 96명
- 차량 42대
- 물류센터 12곳
- 알림 30건
- 운송별 센서·조치 이력 12~40건

### 4.2 대표 데이터 분포

- 운송 상태: 정상, 온도 이탈, 배송 지연, 센서 단절, 조치 완료
- 짧고 긴 기사 이름
- 형식과 길이가 다른 연락처, 운송장 번호, 차량 식별자
- 짧은 화물명과 긴 의약품·검체·신선식품 화물명
- 짧은 허브명과 긴 출발지·목적지 주소
- 음수와 소수점을 포함하는 허용 온도 범위와 현재 온도
- 비어 있는 메모, 짧은 메모, 여러 줄 조치 사유
- 정상·경고·위험 값과 데이터 없음·센서 오류를 구분할 수 있는 값

fixture의 값 분포는 UI 해법을 설명하지 않고 실제 콘텐츠 압력을 만드는 역할만 한다.

## 5. 공통 기능 계약

### 5.1 현황과 테이블

- 운송 현황 KPI와 시간대별 온도 이상 추이를 표시한다.
- 64건 운송을 보여주는 주 데이터 테이블을 제공한다.
- 테이블은 행 체크박스, 전체 체크박스, 상태, 운송장, 화물, 경로, 기사, 차량, 현재 온도, 허용 범위, ETA, 알림 정보를 다룬다.
- 사용자는 열을 정렬하고 날짜, 상태, 허브, 온도 상태, 기사 조건을 적용할 수 있다.
- 여러 행을 선택해 상태 변경이나 담당자 지정 같은 일괄 조치를 수행할 수 있다.

### 5.2 상세와 이력

- 테이블의 운송을 선택하면 현재 화면을 유지한 채 상세 정보를 볼 수 있다.
- 상세에는 기본 정보, 온도 추이, 센서 이벤트, 조치 이력을 포함한다.
- 데이터 양이 표시 영역을 넘는 실제 스크롤 상태를 제공한다.

### 5.3 배차 편집

- 운송 상세에서 배차 편집을 시작할 수 있다.
- 기사 이름, 연락처, 운송장 번호, 기사, 차량, 출발지, 목적지, 운송 상태, 허용 최저·최고 온도, 메모를 편집한다.
- 기사는 96명의 전체 후보에서 선택한다.
- 저장, 취소, 검증 오류, 저장 성공 상태가 실제로 동작한다.
- 변경은 브라우저 메모리에만 반영한다.

### 5.4 알림

- 헤더의 알림 버튼에서 현재 화면을 떠나지 않고 알림 30건을 확인한다.
- 읽음 상태와 처리 상태를 변경할 수 있다.
- 알림 양이 표시 영역을 넘는 상태를 포함한다.

### 5.5 상태와 viewport

- 초기 로딩, 빈 필터 결과, 검증 오류, 저장 성공, 일반 오류 상태를 재현할 수 있다.
- 1440×900과 1024×768 viewport에서 주요 과업을 수행할 수 있어야 한다.

## 6. 의도적으로 지정하지 않는 사항

공통 생성 프롬프트는 다음을 요구하거나 암시하지 않는다.

- input의 너비, 폼 열 수, label 배치
- 검색의 존재 여부, 검색 위치, 검색 범위
- 팝오버·드롭다운·상세 UI의 종료 방법
- 리스트 높이, 스크롤 컨테이너 크기, sticky 여부
- table column 폭, truncation, tooltip 정책
- 색상, radius, shadow, density, spacing, typography
- keyboard shortcut, focus strategy, animation 방식
- 특정 컴포넌트 또는 디자인 시스템

필수 사용자 과업과 데이터 크기만 주고, 해법은 각 조건이 선택하게 한다.

## 7. 기술 구조

### 7.1 공통 런타임

- React
- TypeScript
- Vite
- `lucide-react`
- CSS와 브라우저 기본 API

UI component library와 chart library는 사용하지 않는다. 차트가 필요하면 CSS, HTML, SVG로 구현한다. 세 variant는 동일한 dependency version과 실행 명령을 사용한다.

### 7.2 variant 격리

비교 앱은 하나의 launcher와 세 개의 독립 구현으로 구성한다.

```text
experiments/design-workflow-dashboard/
├── common/
│   ├── product-brief.md
│   ├── functional-contract.md
│   ├── fixtures.ts
│   └── types.ts
├── variants/
│   ├── baseline/
│   ├── design-rules/
│   └── design-workflow/
├── launcher/
├── evaluation/
└── README.md
```

각 variant는 공통 파일의 동일 snapshot을 자기 소스 트리에 복사한다. 공통 React component나 CSS를 공유하지 않는다. launcher는 variant를 X/Y/Z로 여는 기능만 가지며 variant 내부 레이아웃에 관여하지 않는다.

## 8. 생성 절차

1. 오케스트레이터가 공통 brief, 기능 계약, fixture, 타입, dependency shell을 만든다.
2. A/B/C 조건별 입력 package를 고정하고 checksum을 기록한다.
3. 서로 이력을 공유하지 않는 세 컨텍스트에 각 variant 디렉터리의 소유권을 부여한다.
4. 세 생성기에 같은 완료 조건과 검증 명령을 준다.
5. 생성기는 자기 앱을 구현하고 typecheck/build를 통과시킨다.
6. 오케스트레이터는 기능 누락만 확인한다. 디자인 결함을 생성기에 피드백하거나 수정시키지 않는다.
7. 조건별로 기능 누락이 있으면 디자인 해법을 제시하지 않는 동일한 형식의 중립 피드백 한 번만 허용한다.
8. 세 결과를 launcher에 연결하고 X/Y/Z 매핑을 무작위로 만든다.

C가 route를 공개하거나 사용자 승인이 필요한 durable direction을 제안하더라도, 이번 산출물은 폐기 가능한 목업이다. 공통 프롬프트의 제품 brief를 사용자 승인된 과업 제약으로 취급하되, 새로운 프로젝트 기본값을 `adopted`로 기록하거나 managed `DESIGN.md`를 만들지 않는다. 방향이 필요하면 일회성 `candidate`로 사용한다.

## 9. 검증과 블라인드 장면

### 9.1 중립 기능 검증

디자인 점수를 알지 못하는 오케스트레이터 검증은 다음 성공 여부만 확인한다.

- 앱이 실행되고 두 viewport에서 치명적 런타임 오류가 없다.
- 필터와 정렬이 테이블 결과를 바꾼다.
- 행·전체 선택과 일괄 작업이 동작한다.
- 알림을 열고 읽음·처리 상태를 변경할 수 있다.
- 운송 상세를 열고 닫을 수 있다.
- 96명 중 지정된 기사를 선택할 수 있다.
- 배차 편집의 저장, 취소, 오류 상태가 동작한다.
- 빈 결과와 일반 오류 상태를 재현할 수 있다.

이 단계에서는 검색 위치, field 폭, 종료 관행 같은 디자인 피드백을 생성기에 주지 않는다.

### 9.2 캡처 장면

각 variant에서 같은 데이터와 viewport로 다음 장면을 준비한다.

1. 초기 대시보드
2. 필터 UI가 열린 상태
3. 기사 선택 목록을 중간까지 탐색한 상태
4. 알림 UI가 열린 상태
5. 여러 행 선택과 일괄 작업 상태
6. 운송 상세와 긴 이력
7. 배차 편집 폼에 대표적인 짧고 긴 값이 들어간 상태
8. 빈 필터 결과와 오류 상태
9. 1024×768 초기 화면과 주요 overlay

## 10. 숨은 평가표

이 절은 생성 컨텍스트와 생성 전 입력 package에 포함하지 않는다. 가능하면 모든 생성이 끝난 후 평가 도구에 materialize한다.

| 항목 | 배점 | 관찰 기준 |
|---|---:|---|
| 주요 과업 효율 | 20 | 이상 발견, 필터, 선택, 상세 확인, 배차 수정의 단계와 발견 가능성 |
| 정보 위계 | 15 | 위험·경고·정상과 핵심 데이터가 빠르게 구별되는가 |
| 콘텐츠 기반 치수 | 20 | 이름·온도·ID·메모 등 값의 성격과 길이에 맞는 폭·비례인가 |
| UX 관행 | 20 | overlay 종료, 긴 후보 탐색, 검색 범위·위치, 저장·취소·피드백이 자연스러운가 |
| overflow 견고성 | 10 | 긴 목록·테이블·스크롤·긴 텍스트가 겹치거나 숨지 않는가 |
| 접근성 | 10 | keyboard, focus, label, target, contrast, color-independent state |
| 시각 완성도 | 5 | 전체적인 일관성, 정돈, 제품 적합성 |

총점은 100점이다. 표 점수와 함께 각 variant의 가장 큰 장점 3개, 가장 거슬리는 문제 3개, blocker를 기록한다.

### 10.1 정량 관찰

- 기사 96명 중 지정된 기사를 찾고 선택하는 시간과 pointer/keyboard 조작 횟수
- 알림 UI를 pointer로 닫는 방법과 성공 여부
- 이름, 연락처, 운송장, 최저·최고 온도, 메모 field의 실제 렌더 폭
- 1440×900과 1024×768에서 table clipping, overlap, unintended page overflow
- 필터 적용, 전체 선택, 저장, 취소, focus return 성공 여부

정량값은 맥락 없는 단일 합격선으로 자동 판정하지 않고 블라인드 관찰 근거로 사용한다.

## 11. 결과 공개와 2차 실험

사용자가 X/Y/Z를 직접 조작하고 평가표를 확정하면 다음을 공개한다.

- X/Y/Z와 A/B/C의 매핑
- 각 조건에 제공된 스킬 snapshot
- 생성 중 route 또는 판단 로그
- 기능 누락에 대한 중립 재시도 여부
- build와 기능 검증 결과

상위 조건과 하위 조건의 차이가 작거나, 기능 누락이 디자인 평가를 압도하거나, 한 결과가 명백한 생성 실패라면 결론을 유보하고 같은 공통 입력으로 2차 샘플을 생성한다. 2차에서도 새 컨텍스트와 새 랜덤 매핑을 사용한다.

## 12. 거절한 대안

### 공통 wireframe 제공

세 구현의 기능 위치가 같아져 비교는 쉬워지지만, input 폭, 검색 위치, overlay 구조 같은 이번 실험의 핵심 판단을 미리 고정하므로 거절한다.

### 제품명 한 줄만 제공

자유도는 높지만 variant마다 구현 기능이 달라져 스킬보다 scope 차이를 비교하게 되므로 거절한다.

### 생성 중 디자인 피드백 제공

누락을 고칠 수 있지만 숨은 평가 기준을 노출하고 순수 조건을 오염시키므로 거절한다. 기능 계약 누락만 중립적으로 한 번 알릴 수 있다.

### 처음부터 조건당 여러 번 생성

모델 분산을 더 잘 측정하지만 비용과 검토량이 크게 늘어난다. 한 번씩 탐색한 뒤 차이가 불분명할 때만 2차로 확장한다.

### 조건명을 표시한 채 평가

기대 효과가 점수에 영향을 줄 수 있으므로 X/Y/Z 블라인드 평가를 사용한다.

## 13. 완료 조건

- A/B/C가 독립 새 컨텍스트에서 생성되었다.
- 세 variant가 같은 common input과 runtime dependency를 사용한다.
- 각 조건은 자기에게 허용된 스킬만 읽었다.
- 세 앱이 build되고 공통 기능 계약을 수행한다.
- X/Y/Z launcher에서 조건명 없이 조작할 수 있다.
- 동일 장면과 viewport의 캡처가 준비되었다.
- 사용자가 조건 공개 전에 점수와 선호를 기록할 수 있다.
- 조건 공개 자료와 재실험 기준이 준비되었다.
