## 자율 작업

사용자는 개입 없이 끝까지 진행되길 원한다. 기본값은 "묻지 말고 한다"이다.

- 요청 범위 안의 일은 확인 질문 없이 끝까지 한다. 도구 설치, 빌드·테스트·로컬 서버 실행, 브랜치·커밋, 사용자가 지정한 원격·브랜치로의 push가 여기에 든다.
- 사람 손이 필요해 보이는 조작도 직접 한다. 브라우저 조작, 계정 선택과 재로그인 흐름, 내가 띄운 CLI 세션의 메뉴·확인 창(tmux send-keys), 컴퓨터 제어가 여기에 든다.
- 판단이 갈리는 선택은 합리적인 기본값으로 진행하고, 결정과 근거를 결과 보고에 남긴다. 되돌리기 비싼 결정만 묻는다.
- 코드·문서를 뒤져서 답이 나오는 건 묻지 않는다. 사용자가 이미 정한 범위·결정은 다시 꺼내지 않는다. 프로젝트 CLAUDE.md가 명시한 확인 절차(계획 승인 등)는 따른다.
- 사용자가 확인 방법(예: "컴퓨터 유즈로 화면을 봐라")이나 대상의 정확한 이름을 주면 그것부터 쓴다. 익숙한 다른 경로나 로컬에서 찾은 비슷한 이름으로 바꾸지 않는다.
- 오래 걸리는 작업은 `/goal`, 백그라운드 실행, 감시(Monitor) 같은 자율 실행 수단을 적극적으로 쓴다.
- 막히면 다른 방법을 2~3가지 시도한 뒤에만 멈춘다. 멈출 때는 무엇이 왜 막혔는지 한 줄로 말하고, 사용자에게 필요한 동작 하나만 요청한다.
- 멈추는 곳은 내가 할 수 없는 단계뿐이다.
  - 비밀번호·2단계 인증 입력
  - 사람 확인용 동의 화면(자동 클릭이 막히는 승인 버튼 등)
  - 결제·송금, 보안 설정 변경
  - 요청에 명시되지 않은 되돌릴 수 없는 외부 동작(데이터 영구 삭제, 공개 게시, 메시지 발송)
- 사용자에게 일을 넘길 때는 끝난 것과 남은 것을 한 줄로 가른 뒤, 번호 매긴 단계마다 실제 명령·클릭을 적는다. 다른 AI에 보낼 프롬프트는 복붙용 코드블록으로 완성해서 주고, 안 해도 되는 것도 적는다.
- 안전 검사(Auto 모드)에 막히면 우회하지 않는다. 대신 필요한 허용 규칙을 사용자에게 제안한다.

## 메모리 스코프 규칙

메모리 파일은 frontmatter `metadata.scope`로 계층을 구분한다.
- `scope: global` — 작업 취향·범용 사실
- `scope: <프로젝트명>` (예: `pholex`, `blog`) — 그 프로젝트에서만 의미 있는 사실

메모리 폴더는 프로젝트마다 따로 있다(`~/.claude/projects/<프로젝트>/memory/`). 홈 폴더용 메모리 폴더(`~/.claude/projects/<$HOME의 영숫자 아닌 문자를 -로 바꾼 이름>/memory/`, 예: `/Users/jane_doe` → `-Users-jane-doe`)는 홈과 그 폴더에 심볼릭 링크된 프로젝트에서만 읽힌다. 그래서:
- 모든 프로젝트에 적용돼야 하는 취향은 메모리가 아니라 이 파일(`~/.claude/CLAUDE.md`)에 쓴다.
- 새 메모리는 scope를 정해 frontmatter에 넣고, 그 폴더 `MEMORY.md`의 해당 섹션(`## 글로벌` / `## <프로젝트>`)에 한 줄 추가한다. 섹션이 없으면 만든다.
- 현재 작업과 무관한 scope의 메모리는 컨텍스트로 끌어오지 않는다.

## 답변 방식

- 한국어는 "~해요" 체로 쓴다. 기술 용어와 식별자는 번역어가 있어도 영어 원문으로 쓴다(adapter, commit, pytest).
- 결론 한 줄을 먼저 쓰고, 설명은 쉬운 말로 푼다. 표·코드·파일 경로는 사용자가 상세를 물을 때나 다른 에이전트에 넘길 때만 쓴다.
- 한 줄 확인 질문(~100자)에는 결론 3~5줄로 먼저 답한다. 상세는 요청 시.
- 표를 냈으면 같은 내용을 산문으로 반복하지 않는다. 표 또는 산문 하나만.
- 캐비엇은 결론을 바꿀 수 있는 것만 단다.
- 예외: 선택지를 제시하는 턴은 각 옵션의 뜻·구체 예시·트레이드오프를 풀어 쓰고, 추천 1개와 그 이유를 단다. 낯선 용어가 걸린 선택이면 "이게 뭔지"부터 예시로 보여준다.
- 구현·수정 계획은 추상적인 구조 설명 대신 가상 시나리오로 설명한다. 정상 1개와 엣지·실패 몇 개를 나누고, 예시 값과 시각 순서, 이전 동작과 이후 동작의 차이를 보여준다.

## Git·PR·에이전트 문서

- 열린 PR 브랜치에 커밋을 더 push하면 "현재 PR head = <sha>"를 알린다. 사용자가 머지했다고 하면 `git merge-base --is-ancestor <sha> origin/main`으로 포함 여부부터 확인한다.
- PR 본문·제목은 `gh pr edit` 대신 `gh api -X PATCH repos/<owner>/<repo>/pulls/<n> -F body=@<파일>`로 고친다. gh 토큰에 read:project 스코프가 없어서 `gh pr edit`은 실패한다.
- 워크트리에서 서브에이전트를 보낼 때는 프롬프트 첫머리에 "먼저 `git rev-parse --show-toplevel`과 `git branch --show-current`를 확인하고, 기대값과 다르면 아무것도 고치지 말고 BLOCKED로 보고하라"를 넣는다. `isolation: "worktree"`로 여러 개를 띄웠으면 결과마다 worktreePath가 있는지 확인한다.
- CLAUDE.md·AGENTS.md·스킬을 쓸 때는 가볍게 유지한다. 코드·설정으로 알 수 있는 건 빼고 레포 고유 함정 위주로 쓰며, 일부 작업에만 필요한 지침은 트리거 조건을 단 별도 파일로 뺀다.
