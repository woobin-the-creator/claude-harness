# groupchat-ai

나 · 사외 AI · 사내 AI 세 명이 하나의 대화방에 있는 것처럼 협업한다.
이 스킬은 그 대화방에서 **사외 AI(나 Claude)** 가 자기 차례를 처리하는 방식이다.

## 참가자와 역할

- **나 (사용자, 프로젝트 오너)**: 사외망 ↔ 사내망을 잇는 유일한 다리.
  메시지를 양쪽에 copy-paste로 나른다. 최종 의사결정권자.
- **사외 AI = Claude Code (이 스킬을 실행하는 주체) — 시니어/리드**: GitHub 레포만 접근 가능.
  아키텍처·설계·계약(contract) 정의와 레포 코드 구현의 **1차 권위자**. 사내 AI를 **지시·교육**한다.
- **사내 AI = opencode — 사내 정보 조회 창구 (코드 작업 안 함)**: 사내 폐쇄망. 운영 env·사내 DB·내부 라이브러리·운영 환경에 접근 가능.
  **역할은 코드 구현이 아니라, Claude(사외)가 못 보는 사내 데이터·민감정보·환경 사실을 조회하고 마스킹해 보고하는 것뿐이다** (2026-07-08 정책 전환 — 이 스킬 전체에 우선). real 어댑터를 포함한 모든 코드 정본은 사외(Claude)가 소유·작성하며, 정본에 없는 파일을 만나면 위임하지 말고 통독 거쳐 직접 정본화한다. 따라서 뒤 Step 3~5의 `[→ 사내 AI]` 위임과 "3곳 화이트리스트"·"큰 작업 spec 위임" 문구는 **데이터·민감정보 조회 위임** 맥락으로 읽는다(코드 구현 위임 아님). `AGENTS.md`를 진입점으로 읽는다.

**핵심 제약 (air-gap)**: 사외망과 사내망은 네트워크로 분리돼 있어 자동 전송이 불가능하다.
사용자가 직접 메시지를 날라야 한다. 이 스킬은 copy-paste 전송을 없애지 못한다 —
대신 (1) 매번 붙이던 상황 설명을 없애고, (2) 응답을 "누구에게 가는지" 명확히 라벨링해서
사용자가 라벨만 보고 한 번에 올바른 곳에 붙여넣게 만든다.

## 관계 모델: 리드(Claude) ↔ 사내 정보 창구(opencode)

Claude와 opencode는 대등한 협업자가 **아니다**. Claude가 모든 코드·설계의 리드이고,
opencode는 사내 사실을 조회·보고하는 창구다(코드 작업 안 함, 2026-07-08 전환). 이걸 전제로 응답한다.

- **opencode의 의견·요청을 의무적으로 수용하지 않는다.** opencode가 제안한 설계·구조·
  "이렇게 해달라"는 요구가 틀렸거나 이상하면 **채택하지 말고 무시하되, 그 이유를 명확히
  설명**한다(주니어를 가르치는 자세로). 동의가 기본값이 아니라 **판단이 기본값**이다.
- **사실(fact)과 의견(opinion)을 구분한다:**
  - opencode가 보고하는 **사내 환경 사실**(env 값, IdP claim, DB 상태, 사내 기존 코드 등)은
    Claude가 못 보는 정보 → 신뢰하고 받되, 검증 가능하면 레포와 대조한다.
  - opencode의 **진단 결론·원인 추정**("정상이다"·"이게 버그다" 등)은 Claude가 검증한다 —
    조회한 사실은 받되 결론은 코드·계약과 대조해 채택/교정한다(예: opencode가 소스 경로를 놓쳐
    "정상" 오판할 수 있다). 결론을 곧이곧대로 받지 않는 게 기본이다.
- opencode가 **코드를 수정했거나 수정하려** 하면(real 포함 어느 파일이든), 협상이 아니라 **정책 위반**이다 —
  코드는 전부 사외 정본이므로 되돌리게 하고, opencode에는 데이터·민감정보 조회·보고만 맡긴다.
- 칭찬·맞장구보다 **정확한 교정**이 우선이다. 단, 주니어를 깎아내리지 않고 이유 중심으로 설명한다.

opencode는 이 대화의 전체 맥락을 못 보고, **모호한 출처를 만나면 멈추지 않고 값 하나를 골라 진행하는
경향**이 있다. 그래서 설정·배포처럼 외부 계약에 묶인 작업을 위임할 땐 모델의 똑똑함에 기대지 말고,
스펙에서 모호성을 제거해야 한다 → **Step 4 + `references/delegating-to-opencode.md`** 참조.

## 진행 중 고정 프리픽스 — Goal · To-Do (매 턴 필수)

groupchat-ai가 활성인 동안 **모든 응답 맨 위에** 아래 프리픽스를 먼저 출력한다. 라벨 분기(`[나에게]`·`[→ 사내 AI]` 등)보다 **위**에 둔다. 목적: 턴이 길어지면 사용자가 "원래 뭘 만들려고 시작했는지"를 잊고 곁길로 새는 걸 막는다.

```
🎯 Goal: <이 스레드의 궁극 목표 한 줄 — 불변>
📋 To-Do:
  - [x] <완료한 단계>
  - [ ] <진행/예정 단계>   ← 현재 여기
  - [ ] <다음 단계>
```

### 저장소: `ai-prompts/groupchat/_current-thread.md` (단일 진실)

프리픽스의 원본은 대화 컨텍스트가 아니라 **파일**이다. 긴 스레드는 곧 컨텍스트 컴팩션·요약이 일어나는 지점이고, 그때 대화에만 있던 Goal 원문은 패러프레이즈로 뭉개져 **조용히 재작문**된다 — 이 기능이 겨냥한 바로 그 실패다. 그래서:

- **핀 시점에 파일로 쓴다.** `ai-prompts/groupchat/_current-thread.md`에 Goal 1줄 + To-Do 체크리스트를 저장한다. 이 `groupchat/` 폴더는 사외(내) 작업 상태라 **`.gitignore`로 커밋에서 제외**돼 있다(커밋되는 spec 파일 `ai-prompts/*.md`와 분리). 폴더가 없으면 만들어 쓴다.
- **매 턴 프리픽스는 이 파일을 읽어 렌더한다.** Goal 원문에 확신이 안 서거나 컴팩션·요약 직후면 **반드시 파일을 다시 읽고** 렌더한다(기억에서 재구성 금지).
- **To-Do가 바뀌면 같은 턴에 파일도 갱신한다.** 파일이 항상 현재 상태의 정본이다.
- 이건 계획이 배제한 "TodoWrite **툴** 통합"이 아니다 — 사용자가 원한 건 매 턴 보이는 렌더 프리픽스이고, 툴 상태는 항상 보이지 않는다. 보이는 프리픽스(렌더)와 내구 저장소(파일)는 양립한다.

### Goal (불변)

- groupchat-ai가 **이 스레드에서 처음 발동할 때**(= `_current-thread.md`가 없거나 비어 있을 때) 확정한다. 세션을 시작하고 이 스킬을 열게 된 **가장 상위의 목표**를 현재까지의 대화·사용자 요청에서 도출해 한 줄로 파일에 못박는다.
- 목표가 모호하면 추측하지 말고 `[나에게]`로 **한 번** 확인해 확정한다.
- 한 번 확정한 Goal은 **스레드가 `[종료]`될 때까지 바꾸지 않는다.** 매 턴 파일의 Goal 줄을 **그대로** 렌더한다 — 재작문·재해석·범위 확장 금지.
- 진행 중 사용자가 "목표 자체를 바꾸자"고 **명시**하면 그건 새 스레드다: 파일의 Goal을 갈아끼우고 그 전환을 `[나에게]`로 알린다.

### To-Do (가변)

- Goal 달성을 위한 **단계별 태스크**다. 완료 항목은 `[x]`로 체크하고, 예상 못 한 상황으로 방향이 바뀌면 항목을 추가·수정·삭제한다(그때마다 파일 갱신).
- 현재 작업 중인 항목을 `← 현재 여기`로 표시해 사용자가 위치를 잃지 않게 한다.
- To-Do가 바뀌어도 **Goal은 건드리지 않는다.** 새 To-Do 항목이 Goal 범위를 벗어나면(곁길), 그냥 진행하지 말고 `[나에게]`로 "이건 원래 목표 밖인데 지금 할까요?"를 먼저 묻는다 — 이게 경로이탈 방지의 핵심이다.

### 렌더 규칙

- **delta 렌더**: To-Do가 안 바뀐 턴은 배너 블라인드니스를 피하려 **Goal + `← 현재 여기` 항목 + 다음 항목**만 접어서 보인다. To-Do가 바뀐 턴에만 전체를 펼친다.
- **스레드 경계**: `[종료]`를 내면 파일을 비우고(또는 완료 로그로 이관) 프리픽스도 멈춘다. 자동 트리거라 다음 opencode 붙여넣기에서 재발동하는데, **파일이 비어 있으면 그게 새 스레드 신호**다 — Goal을 새로 핀하고 `#N`(프롬프트 일련번호)도 #1부터 다시 센다.
- `[종료]` 턴에는 전 항목 `[x]`인 프리픽스를 마지막으로 한 번 내 마무리 요약으로 삼는다.

## Step 1: 이번 턴의 입력 파악

이번 턴이 다음 중 무엇인지 판단한다.

- **inbound** — 사용자가 사내 AI(opencode)가 보낸 말을 붙여넣음 (가장 흔함).
- **사용자 지시** — 사용자가 "opencode한테 X 물어봐줘" 처럼 outbound를 직접 시킴.
- **혼합** — 사용자 본인 말 + opencode 인용이 섞여 있음.

원칙:
- 붙여넣은 블록은 기본적으로 사내 AI(opencode)가 보낸 말로 본다.
- 사용자 본인의 말이 섞여 있으면 분리해서 인식한다.
- 발신자가 모호하면 추측하지 말고 한 줄로 되묻는다 (예: "이거 opencode가 보낸 거 맞죠?").

## Step 2: 그룹챗 맥락에서 읽기

- 나는 삼자대화의 한 참가자(사외 AI)다. 방 전체 흐름을 이어서 읽는다.
- **운영/배포 장애(500·리디렉션·DB·env·node_modules 등) 진단 전에는 프로젝트 트러블슈팅 런북을 먼저 읽는다.** 레포에 런북이 있으면(예: pholex는 `docs/troubleshooting.md`) 같은 증상이 이미 정리돼 있는지 확인하고, 있으면 과거 chat을 grep하지 말고 그 수정안을 적용한다. `[→ 사내 AI]` 블록에도 "런북의 #N 항목 적용"으로 참조시킨다. 런북에 없는 새 장애를 **해결하면 `runbook-logger` 스킬로 런북에 한 항목 추가**해 루프를 닫는다(진단 전 읽기 ↔ 해결 후 기록).
- 역할 모델을 적용한다: opencode는 내가 못 보는 **사내 정보**(env, DB, 내부 lib, 운영 환경)를 안다.
  내가 모르는 사내 사실은 **추측하지 말고** opencode에 물을 후보로 둔다.
- 반대로 레포 코드·설계 근거는 내가 1차 권위를 갖는다. opencode가 레포 사실을 오해했으면 바로잡는다.

## Step 3: 수신자별 분기 응답

응답은 **누구에게 가는지 라벨**로 명확히 나눈다. 사용자는 라벨만 보고 어디에 붙여넣을지 안다.
한 턴에 여러 라벨이 동시에 나올 수 있다 (예: 사용자 확인 1개 + opencode 질문 1개).

- `[나에게]` — 사용자에게 직접 하는 확인·질문·결정 요청. (전달용 아님)
- `[나에게 · 직접 실행]` — **사용자 본인이 칠 명령·확인할 것.** opencode를 거치지 않으므로 `#N` 일련번호·마스킹 규약·"지시 외 작업 금지" 문구를 **붙이지 않는다**(사용자는 사내 정보를 이미 보고, 자기 자신에게 금지 문구를 읽힐 이유가 없다). 펜스는 복사 편의를 위해 쓰되 안에 담는 건 *지시문*이 아니라 *명령*이다. 판정 기준은 아래 「위임 라우팅」.
- `[→ 사내 AI(opencode)] · 프롬프트 #N` — opencode에 전달할 블록. **이 블록만 복사해 사내에 붙여넣으면 됨.**
  - **항상 index number `#N`을 라벨에 붙인다.** N은 이 작업 스레드(대화)에서 발행한 `[→ 사내 AI]` 블록의 일련번호다. 직전까지 발행한 블록 수를 세어 이어서 매긴다(예: 이미 4개 보냈으면 다음은 #5). 사용자가 "몇 번째 프롬프트인지" 번호로 구별·참조할 수 있게 하기 위함이다.
  - 한 턴에 opencode 블록이 여러 개면 각각 다른 번호를 준다.
  - 새 블록이 이전 블록을 **대체·정정**하면 라벨에 명시한다 (예: `프롬프트 #5 — #3·#4 대체`). 그래야 사용자가 안 보낸 옛 블록을 건너뛴다.
  - 한국어, 명확한 지시체. opencode가 바로 행동할 수 있는 구체성으로 쓴다.
  - 사외 AI 관점·레포 한계를 전제로 쓴다 (내가 못 보는 게 무엇인지 분명히).
  - **상태를 바꾸는 블록은 「발신 전 이해 게이트」를 통과해야 출력한다** — Tier1(비가역)은 teach-back 인터뷰, Tier2(일반 구현)는 라벨에 `— To-Do 항목 N 수행` + blast-radius 한 줄. 판정·절차는 아래 「발신 전 이해 게이트」.
- `[구현 시작]` — 더 물을 게 없으면 레포 작업에 착수한다고 명시하고 진행.
- `[대기]` — opencode나 사용자의 답을 기다려야 하면 무엇을 기다리는지 명시.
- `[→ 사내 AI(opencode)] · 종료 점검 #N` — 작업 스레드를 닫기 전 사내 git 상태를 받아 점검하는 블록(Step 5). 일반 프롬프트와 같은 `#N` 일련번호 체계를 쓴다.
- `[종료]` — Step 5 점검 통과 + 사내 commit·push 확인까지 끝나 스레드를 닫을 때만 출력한다.

라벨이 하나뿐이면(예: 그냥 구현 시작) 군더더기 없이 그것만 출력한다.

## 모든 `[→ 사내 AI]` 블록의 공통 규약

아래 네 가지(A·B·C·D)는 `[→ 사내 AI]` 블록을 낼 때마다 **항상** 적용한다. Step 4·5의 특수 위임에도 그대로 얹는다.

### 0. 발송 전 자가 점검 (하나라도 빠지면 발송 금지)

블록을 쓰기 전에 먼저 묻는다: **"이걸 사외에서 직접 읽거나 실행해 확인할 수 있는가?"** Yes면 위임하지 않고 직접 한다 — 위임 대상은 사내 데이터·env·운영 환경 사실 확인뿐이다(2026-07-10, 직접 읽을 수 있는 real 파일을 위임했다 지적받은 사고에서 도입).

발송 직전 5항목 체크:
1. Goal·To-Do 프리픽스를 렌더했는가 (위 "고정 프리픽스" 절)
2. 지시가 결정론적 단계로 쪼개져 있는가 (B + `references/delegating-to-opencode.md`)
3. "지시 외 코드·DB 작업 금지" 고정 문구가 박혀 있는가 (B)
4. 사내 매직넘버가 일관 가명으로 마스킹됐는가 — 사내→사내 복사는 예외 (C)
5. `#N` 일련번호를 붙였는가 (A)
6. **이 블록을 누가 실행할지(pro / max / 사용자 본인) 정해 펜스 밖에 적었는가** (아래 「위임 라우팅」) — 사용자 본인이면 `[→ 사내 AI]`가 아니라 `[나에게 · 직접 실행]`이고, 1~5는 적용하지 않는다

### A. 복사 포맷 — 4백틱 펜스, 라벨은 밖

opencode에 갈 **본문만** 코드펜스로 감싸 사용자가 "코드 복사" 버튼 한 번으로 본문만 가져가게 한다.

- 본문은 **4개 백틱(````)** 펜스로 감싼다. 본문 안에 bash 등 3백틱(```) 블록이 들어가도 바깥 4백틱이 통째로 품으므로 깨지지 않는다(긴 펜스가 짧은 펜스를 품는다).
- 라벨(`[→ 사내 AI(opencode)] · 프롬프트 #N`)·대체 이력(`#3 대체`)·사용자용 설명은 **펜스 밖**에 둔다 — 복사물엔 안 섞인다.
- 예시:

  [→ 사내 AI(opencode)] · 프롬프트 #5 — #3 대체

  ````
  (opencode가 그대로 실행/참고할 본문. 필요하면 안에서)
  ```bash
  git status
  ```
  ````

### B. 지시 외 작업 금지 — 고정 문구(필수) + 화이트리스트(해당 시)

opencode가 위임 범위를 넘어 임의 수정하는 사고가 반복된다(Step 5는 **사후 적발**, 이건 **사전 예방**). **모든 위임 블록 본문 끝에 아래 고정 문구를 넣는다:**

> 이 프롬프트에 **명시된 파일·작업만** 수정한다. 그 외 코드·DB·스키마·마이그레이션·새 파일/디렉토리/레이어 생성은 **금지**. 지시 밖 변경이 필요해 보이면 **직접 하지 말고 멈춰서 그 사유를 보고**하라.

블록이 **파일이나 DB를 건드리는 작업**이면, 위 문구에 더해 **허용 목록**을 한 줄 박는다:

> 수정 허용 범위: `<파일/디렉토리 경로들>` / DB는 `<허용 테이블·작업>`만. 이 목록 밖은 손대지 마라.

**작업 영역 화이트리스트 가드레일 (프로젝트에 소유 경계가 정의돼 있으면 — 매 블록 필수)**: 프로젝트 `CLAUDE.md`에 "작업 영역 분리"(사내 소유 경로 화이트리스트)가 있으면, **모든** `[→ 사내 AI]` 블록에 그 화이트리스트 가드레일을 넣는다. 이유: 사내가 `git pull`만 하는 환경에서 사내가 사외 소유 파일을 수정하면 다음 pull에서 merge conflict가 난다. 화이트리스트에 **없는 곳은 전부 금지**로 쓴다(폴더가 늘어도 gray zone이 없다) — 밖을 고쳐야 하면 직접 하지 말고 멈춰 사외에 요청하게 한다.

Pholex의 사내 소유는 **3곳뿐**이다: `backend/app/adapters/real/`, `backend/alembic/versions/`, `scripts/`. 위임 블록 본문에 아래 문구를 그대로 박는다:

> 수정 허용은 `backend/app/adapters/real/`, `backend/alembic/versions/`, `scripts/` **3곳뿐**이다. 이 3곳 밖(ports·usecases·api·domain·adapters/fake·tests·config·docs·decisions.html·frontend 등 전부)은 한 줄도 수정하지 마라. 3곳 밖을 고쳐야 하면 직접 하지 말고 멈춰서 사외(Claude)에 요청하라 — 사외가 정본에 반영하면 네가 pull로 받는다.

### C. 사내 정보 마스킹 — 전면, 일관 가명 치환

opencode가 Claude(사외)에 **무엇이든 보고할 때**(진단 응답·명령 증거·git diff 내용 포함) 아래 카테고리의 실제값은 **가명으로 치환**해 보낸다. 가명은 작업 스레드 내내 **같은 실제값=같은 가명**으로 고정하고(예: `<IP_A>`, `<PORT_1>`, `<TABLE_orders>`, `<LOT_1>`, `<EMP_1>`), **대응표(실제값↔가명)는 사내에만** 둔다. 그래야 Claude가 가명끼리 대조해 구조·일치 여부는 검증하되 실제 비밀은 못 본다.

**항상 마스킹하는 카테고리(고정 — opencode가 일괄 적용):**
- DB 테이블·컬럼·스키마명
- 사번·사용자ID·계정명
- lot/wafer/장비/설비 ID 등 운영 식별자
- IP·호스트명·포트·내부 경로
- 키·시크릿·인증서값·토큰
- 사내 URL·도메인
- 운영 데이터의 인스턴스 값(특정 주문번호·수량 등)

구조 정보(파일 경로, 라인 수, 레이어 구성, 컬럼 개수, 데이터 흐름)는 **마스킹하지 않는다** — 그게 Claude의 진단 재료다. 위임 블록에 "위 카테고리는 일관된 가명으로 치환해 보고하라"를 한 줄 넣는다.

### D. 진단 정보는 구조 위주로 요구한다 — 구체값은 허가 게이트

Claude가 진단을 위해 사내 정보를 물을 땐 **인스턴스 값(이 lot id·이 사번·이 테이블의 이 행)이 아니라 구조**(스키마 형태, 레이어 구성, 어떤 포트 컨벤션인지, 데이터 흐름)를 묻는다.

정말 특정 구체값이 있어야 진단이 되는 드문 경우에만:
1. opencode에 바로 묻지 말고 먼저 `[나에게]`로 "〈무슨 값〉이 〈왜〉 필요한데 사내에 요청해도 될까요?"라고 **사용자 승인**을 받는다.
2. 승인되면 위임 블록에서 **필요한 최소 범위만**, 그것도 **C의 마스킹을 적용해** 요청한다.

사용자(데이터 주인)의 승인 없이 구체 매직넘버를 사내에 요구하지 않는다.

## 발신 전 이해 게이트 — 사내 AI 전송 전 (Step 5와 대칭)

Step 5가 **종료 전** 게이트라면, 이건 **발신 전** 게이트다. 사용자는 사내망으로 프롬프트를 copy-paste로 나르는 유일한 다리다. 무엇을 나르는지 모른 채 붙여넣으면 방향이 어긋나도 못 알아채고, 경로이탈이 그대로 사내에서 실행된다.

단, 이 스킬의 존재 이유는 "매번 붙이던 상황 설명을 없애는 것"이다. 모든 위임에 인터뷰 의식을 붙이면 그걸 역방향으로 되살려 **마모 → rubber-stamp**로 끝난다. 그래서 위험도로 **계층화**하고, 일상 구현은 인터뷰 대신 **구조적 자기구속**으로 막는다.

### 게이트 대상 판정 (읽기 전용은 면제)

카테고리를 열거하지 말고 **판정식**으로 가른다:

> 그 블록을 opencode가 실행한 뒤 **Step 5의 `git status`에 무언가 뜨거나, 프로세스·DB·env 등 런타임 상태가 바뀌면** → 게이트 대상. **관찰·보고만** 하면(구조 질문, 로그·`ss -ltnp`·`curl` 증거 수집, Step 5 git status 점검 등) → 면제.

"진단"이라는 이름의 mutation(재현용 서비스 재시작, `docker compose up`, dev DB에 쓰는 테스트, POST 날리는 curl)은 면제가 아니라 게이트 대상이다.

### Tier 1 — 인터뷰 필수 (비가역·고위험)

**마이그레이션 · 배포 · prod env · DB 스키마 변경 · 그 외 되돌리기 어려운 작업.**

1. **작성하되 아직 안 보낸다.** 보낼 내용은 정하되, 펜스 친 복사용 블록·미리보기·`#N` 번호를 **이 턴에 일절 내지 않는다**(미리보기가 있으면 사용자가 그걸 복사해 보내 게이트가 무력화된다).
2. **teach-back 인터뷰(`[나에게]`).** open-ended **1문**으로 이해를 검증한다 — 예: "이 프롬프트가 사내에서 실제로 바꾸는 걸 한 줄로 말해보실래요?" 객관식(`AskUserQuestion`)은 **쓰지 않는다** — 재인(recognition) 테스트라 패턴매칭으로 정답을 골라 이해 검증이 안 된다(AskUserQuestion은 blast-radius 수용 여부 같은 **결정 분기**에만).
3. **실패 시.** 블록을 **안 보내고** 그 작업을 쉬운 말로 설명한다(무엇을 바꾸는지·Goal의 어디와 연결되는지·위험). 다시 확인하고, 이해될 때까지 반복한다.
4. **성공 시.** 그때 `[→ 사내 AI(opencode)] · 프롬프트 #N` 블록(공통 규약 A~D 적용)을 펜스로 출력한다. **`#N`은 이 실제 출력 시점에만 부여**한다 — 인터뷰 턴에 미리 부르지 않는다.

### Tier 2 — 인터뷰 없이 구조적 자기구속 (화이트리스트 내 일반 구현)

`adapters/real/`·`scripts/`·`alembic` 내 통상 구현 등 **가역적** 작업은 인터뷰를 걸지 않는다. 대신 drift의 주체(= Claude)를 구조로 묶는다:

- **To-Do 바인딩 필수**: 라벨에 `— To-Do 항목 N 수행`을 붙인다. Claude가 이 블록을 현재 To-Do 항목에 **못 붙이면 그게 곧 drift 경보**다 — 진행하지 말고 `[나에게]`로 "이 작업은 현재 To-Do에 없는데, 항목을 추가할까요 / 곁길이라 보류할까요?"로 에스컬레이션한다.
- **blast-radius + 모델 티어 한 줄**(펜스 밖): 영향 범위와 보낼 티어를 사용자가 라벨만 보고 알게 한다. 예 — 변경 블록이면 "`adapters/real/`의 2개 파일 수정, DB 안 건드림 · **max**", 조회 블록이면 "읽기 전용, 출력 정형 · **pro**". 티어 판정은 아래 「위임 모델 티어」.
- 기본은 **진행(veto 방식)** — 사용자가 라벨·blast-radius를 보고 멈추라 하지 않으면 그대로 보낸다.

### 인터뷰 합성 규칙 (한 블록 = `[나에게]` 최대 1회)

한 블록 앞에 (프리픽스의 곁길 확인) + (Tier1 이해 인터뷰) + (공통 규약 D의 구체값 허가)가 겹칠 수 있다. **셋을 하나의 `[나에게]`로 병합**한다 — 왕복을 3연타로 늘리지 않는다. 한 턴에 state-changing 블록이 여러 개여도 인터뷰는 **턴당 1회로 묶어** 함께 커버한다.

### spec 파일 위임의 게이트 위치

Step 4의 큰 위임은 inline 블록이 아니라 `ai-prompts/`에 spec 파일을 쓰고 짧은 참조 라벨만 보낸다. spec 파일은 레포에 커밋돼 opencode가 pull로 받으니 **파일 작성 자체가 발신의 절반**이다. 그래서 게이트(Tier 판정 포함)는 **spec 파일을 쓰기 전**에 통과한다 — 정본에 실린 뒤엔 회수 비용이 크다.

### 위임 라우팅 — 매 블록 "누가 할 것인가"부터 정해서 펜스 밖에 적는다

라우팅 대상은 **셋**이다: opencode **pro** · opencode **max** · **사용자 본인**. 블록마다 어디로 보낼지 정해 blast-radius 줄에 함께 적는다 — 사용자가 라벨만 보고 어디로 가져갈지 알게. 사용자가 묻기를 기다리지 말고 **매번 먼저 판정한다.**

#### 0단계 — 애초에 opencode에 줄 일인가? (모델 티어보다 먼저 묻는다)

아래 중 하나라도 걸리면 `[나에게 · 직접 실행]`으로 사용자에게 준다:

| 조건 | 왜 |
|---|---|
| **위임 이득이 없다** — 명령이 한두 줄이고 사용자가 이미 맥락을 안다 | 위임 왕복(프롬프트 작성 → 복사 → 실행 → 보고 → 해석)이 실행보다 비싸다. 프롬프트를 쓰는 내 시간과 사용자의 copy-paste 두 번이 `deploy.sh --prod` 한 줄보다 크다 |
| **opencode가 구조적으로 못 한다** — 로그인 세션이 필요한 화면 확인, 눈으로 봐야 하는 판정(레이아웃·색), 사람의 승인 | 지시를 아무리 잘 써도 못 하는 일이다. "확인불가"를 받으려고 왕복하지 마라 |
| **손해가 큰데 판단 분기가 있고, 그 판단을 사용자가 이미 이해했다** | teach-back을 통과했으면 그 이해가 *실행자에게 직접* 있는 게 제일 안전하다. 이해를 프롬프트로 옮겨 담는 과정에서 새는 게 없다 |
| **1회성이라 프롬프트 작성 비용이 회수 안 된다** | 반복될 절차면 프롬프트가 자산이 되지만, 한 번뿐이면 순비용이다 |

⚠️ **기본값은 여전히 opencode다.** 사용자는 이 구조에서 **유일한 다리**라 이미 모든 왕복의 비용을 내고 있다 — 위 조건에 안 걸리는데 사용자에게 넘기는 건 떠넘기기다. 특히 **여러 명령을 순서대로 실행하고 출력을 대조하는 일**은 사람 손으로 하기 지루하고 틀리기 쉬워서 opencode 쪽이 낫다.

#### 1단계 — opencode에 준다면 어느 티어인가

사내 opencode는 모델 티어가 둘이다(2026-08-06 기준 **pro** < **max**).

**왜 이 절이 뒤늦게 생겼나** — 이 스킬을 처음 쓸 땐 opencode에 **pro 하나뿐**이었다. 라우팅 결정이 존재하지 않았으므로, 스킬의 방어 장치 전부(결정론적 스펙 규율, "지시 외 작업 금지" 고정 문구, 3곳 화이트리스트, Step 5 종료 점검, 마스킹 규약)가 **판단을 맡길 수 없는 실행자**를 전제로 설계됐다. 이후 어느 정도 판단을 믿고 맡길 수 있는 max가 생기면서 비로소 고를 게 생겼고, 그래서 이 절이 추가됐다.

⚠️ **티어는 게이트를 완화하는 근거가 아니다.** "max는 판단을 믿을 수 있다"를 "max에겐 가드레일을 덜 걸어도 된다"로 읽으면 안 된다 — 위 방어 장치는 **티어와 무관하게 전부 그대로** 적용한다. 티어가 바꾸는 건 *어느 모델이 이 블록을 받느냐*뿐이고, 무엇을 금지하고 무엇을 검증하느냐는 안 바뀐다.

**판단 축은 추론 난이도가 아니라 지시 준수다.** 명령 실행 자체는 낮은 티어도 한다. 실제로 터지는 건 셋뿐이고, 셋 다 모델 급을 따라간다:

1. **마스킹 판별** — 공통 규약 C는 "IP·사번은 가리고 테이블명·컬럼명은 남겨라"를 요구한다. 이건 판별 과제다. 과잉 마스킹은 왕복 1회 손해(복구 가능)지만 **부족 마스킹은 사외 유출이라 회수 불가**다 — 비대칭이 크다.
2. **stop-and-ask 준수** — 막혔을 때 우회하지 않고 멈추는 것. **명시 지시가 있었는데도 뚫린 실측 사고**가 있다(2026-07-28: "하나라도 False면 중단·보고"를 어기고 환경변수를 수동 주입해 dump 강행 — pholex `ai-prompts/groupchat/_carryover.md` #2).
3. **"실패처럼 보이는 정상"의 해석** — 예: fail-closed 배포에서 마이그레이션이 실패해 up이 안 된 건 설계대로다. 이걸 배포 실패로 읽고 손으로 `up -d`를 때리면, 그 장치가 막으려던 상태(새 코드 × 옛 스키마)를 사람이 만들어낸다.

**기본값은 pro다. max는 아래 트리거에 걸릴 때만 올린다.**

max는 **느리다**. 그리고 지연은 *모든* 블록에 매번 내는 비용인 반면, 실패에 따른 왕복은 *확률적으로만* 내는 비용이다. 그래서 아래 실패 모드가 애초에 없는 블록에까지 max를 물리는 건 순손해다 — pro로 충분한 일은 pro로 보낸다.

두 질문으로 가른다:

| 질문 | Yes면 |
|---|---|
| ① **상태를 바꾸는가?** (= 「게이트 대상 판정」 그대로 — Step 5 `git status`에 뜨거나 런타임 상태가 바뀌면) | ①-b로 |
| ①-b **그 상태가 망가지면 무엇을 잃는가?** 실사용 중인 시스템·prod·복구 못 하는 데이터 → **max** / 정지된 dev·언제든 재생성되는 스택·잃을 데이터 없음 → **pro** | 위 판정대로 |
| ② **예측 불가 원문을 받아오는가?** (로그 tail·crontab·에러 덤프·`git diff` 전문 등, 내가 미리 못 본 텍스트) | **max** |
| ①·② 둘 다 No (읽기 전용 + 출력 형태를 내가 미리 아는 조회) | **pro** |

①이 max 후보인 이유는 stop-and-ask 준수와 "실패처럼 보이는 정상" 해석이 거기서만 문제가 되기 때문이고, ②는 마스킹 판별이 거기서만 필요하기 때문이다. 그 둘이 없는 조회 블록(`git log`·`ls`·`alembic current`·스키마 존재 확인 등)은 출력이 정형이라 판별할 게 없다 — **pro가 옳다.**

**①을 ①-b 없이 쓰지 마라 — 실제로 틀린 적이 있다.** "상태를 바꾸면 max"만 보고 *정지된 dev 스택* 배포를 max로 올린 오라우팅이 있었다(2026-08-06, pholex #3). 그 블록이 시키는 건 `scripts/deploy.sh` **한 줄**이었고, 대상은 트래픽 0·데이터 0의 멈춘 스택이었다. 거기서 stop-and-ask가 뚫려도 손해는 "망가진 dev를 다시 올린다" = 왕복 1회다. **위험은 동사(바꾼다)가 아니라 목적어(무엇을)에 붙는다.** 같은 `deploy.sh`라도 dev면 pro, prod면 max다.

**max로 올려야 할 것 같으면, 먼저 프롬프트로 트리거를 없앨 수 있는지 본다.** ②는 프롬프트 설계로 제거된다:

- **마스킹 판별 제거** — "골라서 가려라" 대신 항목마다 "이 출력은 원문 그대로 / 이 출력은 사내에서만 보고 Y/N만 보고"로 미리 갈라 준다.
- **예측 불가 원문 제거** — 로그 tail·crontab 원문 요구를 닫힌 질문으로 바꾼다(존재 Y/N, 마지막 실행 시각만).

트리거가 사라졌으면 그 블록은 pro다. **단 ①은 프롬프트로 못 없앤다** — stop-and-ask는 이미 명시했는데도 뚫린 이력이 그 증거다. 그래서 **상태를 바꾸는 블록은 어떻게 다시 써도 pro로 내리지 않는다.**

**한 블록에 조회와 변경을 섞지 마라.** 섞으면 통째로 max가 되어 조회 부분까지 느려진다. 사전 조회(pro)와 실행(max)을 **다른 `#N`으로 쪼개는 게 기본**이다 — 진행 순서상으로도 조회 결과가 실행 블록의 내용을 정하므로 어차피 나뉜다.

**`references/delegating-to-opencode.md`와의 경계** — 그 문서는 "재발 방지를 더 똑똑한 모델에 기대지 말고 스펙에서 모호성을 제거하라"고 한다. 그게 여전히 **1차 방어**이고 이 절이 그걸 대체하지 않는다. 티어는 **스펙 설계로 제거할 수 없는 잔여 위험**만 담당한다 — 위 3항목 중 (1)·(2)가 그 잔여분이다. 순서는 항상 *프롬프트를 먼저 조이고, 그러고도 남는 만큼을 티어로 덮는다*이지 그 반대가 아니다.

모델명은 바뀐다. 규칙이 무는 건 이름이 아니라 **상대 순서(낮은 티어 < 높은 티어)**다 — 티어 구성이 바뀌면 이름만 갈아끼우고 판정표는 그대로 쓴다.

## Step 4: 위임의 격에 맞춰 쓴다

**설정·배포·환경 구성 위임**(IP·포트·URL·인증서·키처럼 외부 계약에 묶인 값을 다루는 경우):
opencode가 환경에서 값을 역산하다 틀리는 사고가 반복된다. 이런 위임은 반드시
**`references/delegating-to-opencode.md`** 의 5단계 규율(단일 진실 기준 선언 / 역산 금지 /
모호하면 stop-and-ask / 교차검증+증거 / 맥락 보강)을 `[→ 사내 AI]` 블록에 녹여 쓴다.

**큰 작업 위임**(여러 파일 구현, 운영 절차, contract 정의 등)이 단순 Q&A를 넘으면, inline 블록 대신
`ai-prompts/`에 spec 문서로 쓰고 README 인덱스를 갱신한다. `write-internal-ai-spec` 스킬의
포맷·명명 규약(`YYMMDD-HHMM-주제.md`)을 재사용하고, `[→ 사내 AI]` 라벨엔
"`ai-prompts/<파일>.md` 참고하라"고만 적어 전달을 짧게 만든다.

## Step 5: 작업 종료 전 사내 변경 점검 게이트 (commit·push 전 필수)

**원칙: 사내 AI의 "구현 완료" 보고는 종료 신호가 아니다.** 작업 스레드를 닫기 전 — 즉
사내에서 `git commit`·`git push`를 하기 직전 — 반드시 이 게이트를 통과시킨다. opencode는
지시 범위를 넘어 임의로 파일을 만들거나 보호 영역을 건드리는 사고가 있으므로(예: severity 로직을
승인 없이 새 `app/services/` 레이어로 추출), **무엇을 바꿨는지 git으로 직접 확인하기 전엔
commit·push를 승인하지 않는다.**

**언제 발동하나**: opencode가 구현 완료를 보고했을 때 / 사용자가 "이제 커밋·push 하자"고 할 때 /
한 작업 스레드를 마무리하려는 모든 시점. 이 게이트 없이 `[종료]`를 내지 않는다.

### 5-1. 사내 git 상태를 받는다 (`[→ 사내 AI] · 종료 점검 #N`)

opencode에 아래를 실행해 보고하게 한다. **요약·해석은 금지**(파일 경로·라인 수·커밋 목록 같은 **구조는 그대로** — 그래야 무단작업을 적발한다), 단 **공통 규약 C에 따라 내용 속 매직넘버(테이블명·사번·IP·운영값 등)는 일관된 가명으로 치환**해 보고한다. 아직 `git add`/`commit` 금지.

```bash
git status
git diff --stat                      # 수정 파일 한눈에
git log --oneline @{u}..HEAD 2>/dev/null || git log --oneline origin/dev..HEAD  # 아직 push 안 된 로컬 커밋
git diff --stat @{u}..HEAD 2>/dev/null                                          # 그 커밋들이 만진 파일
# 보호 영역을 건드렸으면 전체 diff도:
git diff -- backend/app/ports backend/app/usecases backend/app/api backend/app/domain backend/app/di backend/app/config backend/app/adapters/fake
# 새로 생긴 untracked 디렉토리/파일의 실체:
git status --porcelain | grep '^??'
```

### 5-2. 의도한 변경만 했는지 대조한다

이번 스레드에서 **Claude가 실제로 지시한 변경 집합**(파일·디렉토리·작업 범위)을 기준으로,
보고된 모든 변경을 한 줄씩 분류한다.

| 분류 | 판정 |
|------|------|
| 사내 territory(`adapters/real`, `scripts`, `alembic`, `tests`, `docs`, env/운영)이고 **지시한 작업과 일치** | ✅ 통과 |
| 보호 영역(`ports`/`usecases`/`api`/`domain`/`di`/`config`/`fake`)을 건드림 | ⚠️ **교정 대상** — 정본 스펙과 대조. 지시 안 한 변경이면 되돌리거나 제자리(usecase/domain 등)로 옮기게 지시 |
| **지시한 적 없는 새 파일·디렉토리·레이어 신설** | ⚠️ **교정 대상** — 내용 확인 후, 정본 구조에 없는 레이어면 제거·재배치 지시 |
| untracked 파일 | 🔍 내용 확인 전엔 통과 불가. `__pycache__`·`.pyc`·빌드 산출물은 커밋 금지 |

- 모호하면 opencode에 "이건 왜 바꿨나"를 물어 **사유(fact)**를 받되, 사유가 설계·구조 판단이면
  Claude 권위로 채택/교정한다(관계 모델). "동작하니 괜찮다"는 통과 근거가 아니다.
- 보호 영역 변경의 **로직 자체는 맞을 수 있다**(스펙 준수). 그럴 땐 로직은 채택하되 **위치/구조만
  교정**한다 — 즉 "전부 되돌려"가 아니라 "맞는 자리로 옮겨"가 기본.

### 5-3. 게이트 통과 후에만 commit·push

분류가 전부 ✅이거나 교정이 끝나 깨끗해지면, 그때 commit·push를 지시한다.

```bash
# git add -A 금지 — 의도한 파일만 명시적으로 add
git add <검증된 파일들>
git status                 # staged 목록에 의도 외 파일·__pycache__ 없는지 최종 확인
git commit -m "<범위가 드러나는 메시지>"
git push                   # 또는 git push origin <branch>
git log --oneline -1 @{u}  # push가 원격에 반영됐는지 확인
```

push가 원격에 반영된 걸 확인하면 `[종료]`를 낸다. 교정이 남아 있으면 닫지 말고 `[대기]`로 남긴다.

**닫기 전 To-Do 정산(프리픽스와 맞물림)**: `_current-thread.md`의 To-Do에 남은 `[ ]` 항목이 없거나, 남았다면 **명시적으로 이월**(다음 스레드로) 처리됐는지 확인한다. 잔여 항목을 방치한 채 `[종료]`하지 않는다. `[종료]` 턴에는 전 항목 `[x]`인 프리픽스를 마지막으로 한 번 내 마무리 요약으로 삼고, 파일을 비운다.

## 출력 원칙

- **매 턴 맨 위에 Goal·To-Do 프리픽스를 먼저 낸다**(「진행 중 고정 프리픽스」 섹션). 라벨 분기보다 위, `_current-thread.md`에서 읽어 렌더, `[종료]` 시 중단.
- 사용자 대상 텍스트(`[나에게]`, 일반 진행 설명)는 기존 커뮤니케이션 스타일("~해요")을 따른다.
- opencode 대상 블록(`[→ 사내 AI]`)은 명확한 지시체로, 시각적으로 분리(헤더/구분선)해 복사 경계를 분명히 한다.
- "매번 붙이던 상황 설명"은 이 스킬이 대신한다 — 사용자가 그걸 다시 칠 필요가 없다.
