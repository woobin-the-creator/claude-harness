# 스펙 초안을 먼저 내고, 빈칸만 인터뷰한다

이 스킬은 방향이 뒤집혀 있다. **내가 사용자를 심문하지 않는다 — 내가 스펙 초안을 테이블에 올리고, 사용자가 그걸 심문한다.**

추상적인 질문에 답하는 것보다 구체적인 문서에서 틀린 곳을 짚는 게 사람에게 훨씬 싸다. 그리고 사용자는 대개 한두 번 답하고 다음 일로 넘어간다 — 그 시점에 손에 남는 게 있어야 한다.

흐름은 넷이다: **① 사실을 채운다 → ② 초안을 낸다 → ③ 빈칸만 묻는다 → ④ 원장을 갱신한다.**

---

## ① 묻기 전에 사실을 채운다

사용자의 주의는 이 세션에서 가장 비싼 자원이다. 레포가 이미 답을 갖고 있는 질문에 그걸 쓰면 안 된다.

코드 조사는 **읽기 전용 탐색 서브에이전트(`Explore`)에 위임한다**. 한 번 보내고, 무엇을 알아와야 하는지 구체적으로 적어 보낸다:

- 이 요청이 닿는 파일과 그 안의 **현재** 동작 — `경로:행`으로
- 이미 같은 일을 하는 곳 — 초안이 따라야 할 모양(명명, 스키마, 테스트 패턴, 에러 처리)
- 이미 결정돼 있는 것 — `CLAUDE.md`/`AGENTS.md`, 설계 문서, 과거 결정 원장

직접 읽는 건 활성 `CLAUDE.md`/`AGENTS.md` 정책이 허용하는 경우만이다(대개 파일 3개 이하, 방금 한 편집 확인, 그대로 베껴야 하는 스타일).

레포가 아닌 것을 다룰 때도 규칙은 같다 — **사실은 내가 찾고, 결정은 사용자가 한다.**

## ② 스펙 초안 — 한 화면

초안은 요청의 요약이 아니라 **약속**이다. 모든 줄이 사용자가 손가락으로 짚고 "틀렸다"고 말할 수 있을 만큼 반증 가능해야 한다.

사용자의 요청은 대개 이미 `1. 2. 3.` 번호 목록으로 온다. **그 번호를 유지해라** — 자기 목록의 3번이 어떻게 해석됐는지 한눈에 대조할 수 있다.

크기는 변경에 맞춘다. 두 줄짜리 변경엔 두 줄짜리 스펙이면 충분하다.

```
## 만드는 것
<사용자에게 보이는 변화, 1~3문장>

## 동작 계약
1. <사용자 목록의 1번> — <X하면 Y한다. 관찰 가능한 문장으로>
2. ...

## 손대는 자리
- `path/to/file.ts:120` — <무엇을>

## 하지 않는 것
- <범위 밖. 있으면 좋지만 이번엔 아닌 것>

## 미결
[?1] <한 줄 질문> — 잠정: <추천안>
```

### 접근 자체가 안 정해졌으면 초안을 여러 개 낸다

위 형식은 **어떻게 만들지가 이미 정해진** 경우다. 그린필드거나 방향이 갈리면 초안 하나를 내는 순간 사용자는 고를 기회를 잃는다 — 초안이 곧 결정이 되어 버린다.

이때는 `## 만드는 것`까지만 공유하고 **접근 2~3개를 나란히** 낸다. 각각에 대해 셋을 적어라: 무엇이 달라지는지 한 줄, 대가(무엇을 포기하는지), 추천 여부. 그다음 `[?1] 접근 선택`을 첫 빈칸으로 올린다 — 이 답이 나머지 빈칸의 선택지를 통째로 바꾸므로 **항상 첫 라운드에 단독으로** 묻는다.

접근이 정해지면 그 하나로 위 형식의 초안을 다시 낸다. 기각한 접근과 이유는 그 자리에서 결정 원장에 박아라 — 안 그러면 다음 세션이 같은 걸 다시 제안한다.

접근이 몇 개나 필요한지는 되돌리기 비용으로 정한다. 나중에 싸게 바꿀 수 있으면 하나만 내고 원장의 **가정**에 적는다.

두 가지를 지켜라:

- **초안은 요청을 넓히지 않는다.** 사용자가 말한 것 + 그게 성립하려면 반드시 필요한 것만 담는다. 있으면 좋을 것은 전부 "하지 않는 것"으로 내려라. 모델이 스펙을 쓰면 기능이 늘어나는 게 기본 실패 모드고, 늘어난 기능은 사용자가 승인한 적 없는데 구현 세션에선 승인된 것처럼 보인다.
- **미결에도 잠정안을 적는다.** 사용자가 "다 좋아"라고만 해도 초안이 그대로 실행 가능해야 한다.

## ③ 무엇이 빈칸이 되나

> 어느 쪽으로 답해도 같은 코드를 쓴다면, 그건 빈칸이 아니다.

- 레포·문서·git이 답하는 것 → 찾아라. ①에서 이미 했어야 한다
- 한쪽이 관례이고 다른 쪽은 "가능"일 뿐인 것 → 관례를 택하고 원장의 **가정**에 적어라
- 싸게 되돌릴 수 있는 것 → 하나 골라라. 사용자가 아니면 말한다

빈칸 개수는 예산이 아니라 **초안 품질의 신호**다. 실측 중앙값은 2~3개였다. 여섯 개를 넘으면 조사가 덜 됐거나 스스로 정할 수 있는 걸 미룬 것이다 — ①로 돌아가 절반을 스스로 답해라.

### 반대 방향으로도 틀린다

위 필터는 **너무 많이 묻는 것**만 막는다. **물어야 할 것을 안 묻는 것**은 못 막고, 실측에서 실제로 이쪽이 났다 — 사용자가 "더 확실하게 붙잡아주는 수단이 필요하다"고 명시한 요구에 대해, 스스로 "이건 한 스텝만 늦출 뿐"이라고 인정한 약한 방법을 골라 놓고 묻지 않았다.

그래서 위 필터보다 **먼저** 걸리는 조건을 하나 둔다:

> 선택지들 사이의 트레이드오프가 크고 그 대가를 사용자가 치른다면, 다른 어떤 이유로도 스스로 정하지 마라. **빈칸이다.**

트레이드오프가 크다는 건 한쪽을 고르면 다른 쪽에서 **되돌리기 어려운 것을 잃는다**는 뜻이다 — 강제력 대 유연성, 안전 대 속도, 지금의 단순함 대 나중의 확장성, 자동화 대 통제권. 어느 쪽이 옳은지는 코드가 아니라 **사용자가 무엇을 더 아프게 느끼는가**로 갈리고, 그건 레포 어디에도 안 적혀 있다.

특히 **사용자가 입 밖에 낸 요구를 충족하는 방법이 여럿이면 무조건 빈칸이다.** 그 항목을 말했다는 것 자체가 거기에 신경 쓰고 있다는 신호다. 네가 하나를 골라 버리면 사용자는 자기가 요구한 것이 **어떤 방식으로** 이뤄지는지 볼 기회를 잃는다.

"관례가 있다"와 "싸게 되돌릴 수 있다"는 이 조건을 무효화하지 못한다. 관례는 트레이드오프를 해소한 게 아니라 **과거의 누군가가 이미 한쪽을 골라둔 것**이고, 이번 사용자가 같은 선택을 할 이유는 없다.

이 조건으로 빈칸이 여섯을 넘으면, 줄일 것은 이쪽이 아니라 **다른 종류의 빈칸**이다. 조사로 없앨 수 있는 걸 더 없애라.

### 묻는 방법

순서는 **다른 빈칸의 답을 바꾸는 것부터**다. `[?2]`의 선택지가 `[?1]`의 답에 따라 달라진다면 `[?2]`는 다음 라운드다.

각 빈칸마다 산문으로 셋을 낸다:

1. 구체적인 선택지 2~3개 (열린 질문 금지)
2. 각 선택지가 **다운스트림에서 무엇을 바꾸는지** 한 줄 — 이 줄을 못 쓰면 빈칸이 아니다. 지워라
3. 추천 하나와 그 이유

그다음 **고르기만** 툴로 받는다. 구조화된 선택 툴(Claude Code의 `AskUserQuestion`)이 있으면 그걸로 띄운다 — 서로 독립인 빈칸은 한 번에 최대 4개까지 묶어 왕복을 줄인다. 그 툴이 없으면 산문에 A/B/C를 달아 두고 사용자가 글자로 답한다.

**산문을 툴 안으로 밀어 넣지 마라.** 선택지 label은 1~5단어라, 대가와 다운스트림을 거기 넣으면 증발한다. 실측에서 값이 가장 컸던 게 그 두 줄이다. 툴은 클릭을 받는 자리지 설명하는 자리가 아니다.

**대가를 안 적으면 라운드가 늘어난다 — 실측이다.** 08-26 CSV export 세션에서 접근 선택 하나에 3라운드를 썼다. 사용자가 우유부단해서가 아니다. 1라운드 답은 "만약 페이지에서 걸어놓은 필터를 거친 데이터를 뽑고싶다면, 클라이언트 생성 방향으로 가야해?"였고 2라운드 답은 "전부 백엔드로 갈 경우 트레이드오프가 뭔지 예시를 들어 설명해줘"였다 — 둘 다 위 2번과 3번이 **첫 메뉴에 있었어야 할 것**을 캐물은 거다. 대가 한 줄은 예의가 아니라 왕복 절감 수단이다.

### 사용자가 되물으면 — 같은 메뉴를 다시 띄우지 마라

"A는 어떤 식으로 해결되는 거야?", "B로 가면 트레이드오프가 뭐야?" — 실측에서 반복된 반응이다. 답하고 같은 빈칸을 다시 물어라. 되묻기는 사용자의 실수가 아니라 **선택지가 덜 구체적이었다는 신호**다.

그런데 실측에서 여기를 틀렸다. 08-26 세션에서 같은 빈칸을 세 번 물었는데 **선택지 label이 세 번 다 글자 그대로 같았다** — `C. 하이브리드 (추천) / A. 전부 클라이언트 / B. 전부 백엔드`. 바뀐 건 질문 앞 문장뿐이었다. 답변은 대화 속으로 흘러가고, 사용자가 실제로 클릭할 자리에는 처음과 똑같은 메뉴가 남았다.

> 되물음의 **내용이 곧 빠진 정보**다. 그걸 선택지 안으로 접어 넣기 전에는 다시 묻지 마라.

두 번째로 물 때 최소한 하나는 달라져야 한다:

- **label이 달라진다** — 되물음이 가리킨 축으로 후보를 다시 쪼갠다(`B. 전부 백엔드` → `B1. 백엔드 · 필터 결과 전량 전송` / `B2. 백엔드 · 현재 창만`)
- **후보가 줄어든다** — 답하면서 탈락한 것을 지운다. 셋을 그대로 유지하는 건 방금 답한 내용이 아무것도 좁히지 못했다는 뜻이고, 그건 답이 빗나갔다는 신호다
- **빈칸이 쪼개진다** — 되물음이 실은 두 결정이 얽혀 있었다는 뜻이면 둘로 나눠 각각 묻는다

셋 중 아무것도 못 하겠으면 **더 물을 게 없는 것이다.** 추천안으로 확정하고 원장 `근거` 열에 `되물음 후 기본값 확정`으로 적어라.

**라운드 수에는 상한을 두지 마라.** 실측 6건의 라운드 중앙값은 1이고(1·5·1·1·1·1), 유일한 5라운드 세션은 사용자가 정당한 정보를 두 번 요구한 결과였다. 상한이 걸렸다면 사용자가 B의 대가를 보기 **전에** 닫혔을 것이다. 길어짐은 라운드 수의 문제가 아니라 **안 움직이는 메뉴**의 문제다.

### 눈으로 볼 문제는 보여줘라

빈칸이 "어떻게 보이나"에 관한 것이면 서술이 렌더를 못 이긴다. 요구받기 전에 제안해라 — `show-design-sample`로 후보를 띄우고 그중에서 고르게 한다. 실측에서 사용자가 세 번 직접 요구했다("a, b, c 버튼을 프리뷰 페이지 위에 시안으로 하나씩 보여줘").

### 빠져나갈 문

사용자가 "나머지는 추천대로"라고 하면 즉시 끝낸다. 남은 빈칸을 전부 추천안으로 확정하되, 원장에는 **사용자가 고른 것이 아니라 기본값으로 확정된 것**으로 구분해 적어라. 그 구분이 사라지면 나중에 뒤집을 때 무엇을 재검토해야 하는지 알 수 없다.

## ④ 결정 원장

**매 라운드 끝에 갱신한다.** 마지막에 한 번 쓰는 물건이 아니다 — 대화가 중간에 다른 데로 새는 게 정상이고, 언제 끊겨도 남아 있어야 한다.

```
## 결정 원장 — <주제>

| # | 결정 | 고른 것 | 근거 | 기각한 것 — 이유 |
|---|------|---------|------|------------------|
| 1 |      |         | 사용자 선택 / 추천안 기본값 |  |

**가정** — 내가 기본값으로 정한 것. 틀리면 말해라
- `<가정>` — `<왜 이 기본값인지>`

**미결**
- `[?N]` <남은 것>
```

기각한 대안과 **그 이유**가 원장의 핵심이다. 이유 없이 "B 기각"만 적으면 다음 세션이 B를 다시 제안하고 사용자가 같은 설명을 또 한다. 가정에는 사용자가 이견을 낼 만한 것만 넣어라 — 그럴듯해 보이려고 자명한 것으로 채우면 진짜 가정이 묻힌다.

`근거`는 그 줄이 사용자가 고른 것인지 내가 추천안대로 확정한 것인지를 가른다. §"빠져나갈 문"이 요구하는 구분이고, 나중에 결정을 뒤집을 때 **무엇을 재검토해야 하는지**가 여기서 갈린다.

원장은 대화 안에 산다. 파일로 떨구는 건 두 경우다: **이제 만들 작업이면 항상**(스펙 파일이 구현 세션에 넘어가는 유일한 산출물이다 — 아래 "구현 세션으로 넘기기"), 그리고 만들지 않더라도 사용자가 요청하거나 이 설계가 이번 작업보다 오래 살 때 → `docs/woobin_plan/specs/YYYY-MM-DD-<topic>-design.md`. 결정 서너 개짜리 비구현 논의면 파일은 중복이다.

**이 작업이 PR이 될 거라면, 자동 확정분은 PR 본문에 남긴다.** 대화에 남은 원장은 세션과 함께 사라지고, 스펙 파일은 레포에 남지만 머지 뒤에 그걸 다시 여는 사람은 드물다 — 리뷰어가 보는 곳은 PR 본문이다. 사용자가 고른 줄은 대화에 기록이 있지만, **내가 묻지 않고 확정한 줄과 가정은 어디에도 없다.** 그것만 적는다:

```
### 자동 확정된 결정
- <결정> — <고른 것>. 기각: <대안> — <이유>

### 가정
- <가정> — <왜 이 기본값인지>
```

원장 전문을 옮기지 마라. PR 본문은 스펙 파일을 가리키는 포인터가 기본값이고 이건 그 규칙의 **좁은 예외**다 — 포인터가 가리킬 소유자가 머지 후 0이 되는 항목에만 적용된다.

파일로 쓸 때는 형식을 맞춘다. 읽는 쪽이 이 대화를 못 본 세션이기 때문이다. frontmatter에 `slug`·`confirmed_at`을 두고, 본문은 여덟 절이다 — Problem / Goals / Non-goals / Decisions / Acceptance criteria / Rejected alternatives / Provenance / Open questions. 원장 표는 Decisions와 Rejected alternatives 둘로 나뉘어 들어가고, **가정**은 Decisions 안에 기본값으로 표시한다.

**Open questions가 비어 있지 않으면 그건 확정 스펙이 아니다.** 파일로 쓰지 말고 대화에서 마저 물어라. 미결을 남긴 채 넘기면 다음 세션이 그 자리를 자기 판단으로 메우고, 그 판단은 사용자가 승인한 적 없는데 구현 세션에선 승인된 것처럼 보인다.

**원장이 원본이고 PR 본문의 자동 확정 절은 옮겨 적은 것이다.** 두 곳이 다른 말을 하기 시작하면 원장(스펙 파일)이 이긴다.

미결이 비면 최종 원장을 낸다. 그다음은 **사용자가 합의를 이미 말했는지**로 갈린다.

- **아직 안 말했으면 멈추고 기다린다.** 구현을 시작하지 않는다.
- **이미 말했으면 멈추지 마라.** "나머지는 추천대로", "그걸로 가자", "좋아" 는 전부 합의 표명이다. 원장을 확정하고 바로 다음 단계로 넘어가라 — 만들 작업이면 아래 "구현 세션으로 넘기기"까지 이어서 끝낸다.

실측에서 이걸 틀렸다. 사용자가 "나머지는 추천대로 가자"라고 한 **뒤인데도** 원장만 내고 "이대로 진행할까요"를 다시 물어, 사용자가 방금 없앤 왕복을 되살렸다. **확인을 한 번 더 받는 건 안전한 기본값이 아니다** — 이미 준 답을 다시 요구하는 것이고, 그 사이 사용자는 이 대화를 떠난다.

## 구현 세션으로 넘기기

다룬 것이 **이제 만들 작업일 때만** 해당한다. 이미 내려진 결정이나 문서·논증을 따진 거였으면 원장에서 끝낸다.

계획서는 쓰지 않는다. 이슈 #41의 A/B 실측 2회에서 계획서 경로는 자유 구현보다 비용 1.8~2.7배·시간 2~3배였고, 품질 이득은 계획서가 아니라 **구현 전 빈틈 찾기와 구현 후 독립 리뷰**에서 나왔다. 그 둘만 남긴다. 스펙 파일 하나가 세 단계를 꿴다:

```
① 스펙 파일 저장 ─▶ ② spec-reviewer ─▶ ③ 구현 세션을 연다 ─▶ 한 세션 구현 ─▶ ④ code-reviewer ─▶ e2e 증명 ─▶ ready
```

### ① 스펙 파일을 저장한다

사용자가 확인하면 **같은 세션에서** 원장을 `docs/woobin_plan/specs/YYYY-MM-DD-<slug>-design.md`로 쓴다(형식은 §④). 기억으로 넘기지 마라 — 특히 기각한 선택지와 그 이유가 파일에 도달해야 한다.

Acceptance criteria에는 사용자가 말하지 않아도 두 항목이 **기본으로** 들어간다. A/B에서 자유 구현이 이긴 핵심이 끝까지 돌리는 자동 e2e였다:

- 끝에서 끝까지의 동작을 **자동 e2e로 증명하고, 새 clone에서 재현**한다. 완료 증거가 커밋 안 된 스크립트에만 있으면 재현 불가다.
- 구현 후 `woobin-harness:code-reviewer` 1사이클을 돌려 findings와 처리 결과를 PR 본문 `### 리뷰` 절에 기록한다.

`.claude/kickoff.local.md`가 있으면 이 시점에 `stage: impl`로 바꾼다. 구현 세션은 스펙 파일만 받으므로 상태 파일을 모른다 — 전환은 여기서 한다.

### ② 스펙 리뷰를 돌린다

`spec-reviewer-prompt.md`의 템플릿으로 `woobin-harness:spec-reviewer`를 **항상** 띄운다. 스펙이 짧아도 띄운다 — 1차 실측에서 빈틈 찾기 이득(기본값 13개·문서 충돌 6개·스펙 재검토 19개)은 전부 이 단계에서 나왔다. 돌아온 findings는 대화가 아니라 **스펙 파일에** 반영하고, frontmatter에 `spec_review:` 한 줄(날짜·건수)을 남긴다. Open questions가 생기면 파일로 넘기지 말고 대화에서 마저 묻는다.

### ③ 구현 세션을 연다

리뷰 반영이 끝나면 **인터뷰 세션이 직접 새 세션을 연다.** 사용자에게 `/clear`를 시키지 않는다. 이 워크플로우의 유일한 필수 세션 경계는 여기다 — 인터뷰 컨텍스트 위에서 구현을 시작하면 요청마다 그 컨텍스트를 다시 읽는다(2차 실측에서 오케스트레이터 비용의 가장 큰 항이 평균 265k 컨텍스트 재독이었다. 플래닝 잔재 ~155k가 구현 캐시 비용의 44%였던 실측도 있다 — `home/HARNESS-LOG.md` #5).

서브에이전트가 아니라 **실제 세션**이어야 한다. 서브에이전트는 Agent 툴이 없어 `Explore`·`screenshot-verifier`에 위임하지 못하고, 사용자에게 묻지 못하며, UserPromptSubmit·Stop 훅(R6·R13 핸드오프, kickoff-guard) 밖이라 컨텍스트 소진에 조용히 끊긴다. 새 세션은 셋 다 갖는다.

여는 수단은 둘이고 순서대로 시도한다:

1. **Paseo** (`create_workspace`·`create_agent` MCP 툴이 있을 때) — `paseo-handoff` 스킬의 절차를 따른다. 워크트리 격리(`isolation: "worktree"`, `mode: "branch-off"`, `baseBranch`는 기본 브랜치), provider는 `claude/opus`, `initialPrompt`는 아래 한 줄, `notifyOnFinish: true`. 기다리거나 폴링하지 않는다 — 끝나면 알림이 온다.
2. **`claude -p`** (Paseo가 없을 때) — 기본 브랜치 기준 워크트리를 만들고 그 안에서 `claude -p "<아래 한 줄>" --permission-mode acceptEdits`를 **백그라운드**로 띄운다. 출력 파일을 Monitor로 걸어 draft PR URL과 종료만 받는다.

어느 쪽이든 넘기는 프롬프트는 **스펙 파일 경로 하나**다:

```
docs/woobin_plan/specs/<date>-<slug>-design.md 기준으로 구현해줘. 절차는 interview 스킬의 "구현 세션으로 넘기기" ③ 절차를 따른다.
```

연 뒤 인터뷰 세션은 사용자에게 세션·워크트리·브랜치 이름을 한 줄로 알리고 **역할을 끝낸다.** 구현 결과를 자기 컨텍스트에서 다시 처리하지 않는다(`home/HARNESS-LOG.md` #7 — 결과를 오케스트레이터가 직접 만지면 요청 수 3배). 사용자가 "지켜볼게"라고 하면 예외다 — 그때는 `/clear` 후 직접 구현으로 안내한다.

구현 세션의 절차는 짧다:

1. **첫 턴**: 브랜치를 만들고 스펙 파일을 첫 커밋으로 push한 뒤 **draft PR**을 연다. 이게 하드 컷·컨텍스트 소진 뒤의 회복 진입점이다. 제목·본문은 `explain` 스킬을 실제로 호출해 "겪던 문제 → 어떻게 풀었나" 서사로 쓴다. 본문은 스펙 파일 포인터 + 자동 확정 결정만.
2. 논리 단위마다 커밋한다. 레이어·구현자 분리는 없다 — 한 세션이 끝까지 만든다.
3. 코드 조사는 `Explore`에, 화면 확인은 `screenshot-verifier`에 위임한다(R4·R5).
4. 다 만들면 `woobin-harness:code-reviewer`에 **스펙 경로 + `origin/main..HEAD`** 를 넘긴다. diff를 붙여넣지 않는다. findings를 반영하고 PR 본문 `### 리뷰` 절에 건수와 처리 결과를 적는다.
5. e2e 증명을 돌리고, `explain`을 다시 호출해 제목·본문을 "어떻게 풀었나"로 갱신한 뒤 `gh pr ready`. create 시점엔 "어떻게 풀었나"가 존재하지 않았다.
6. 머지는 사용자가 한다.

### 이 경로가 안 맞는 경우

세션 하나를 넘는 크기, 파일이 겹치지 않는 병렬 트랙, 마이그레이션·운영 위험 작업은 아직 실측하지 않았다. 그런 작업이 오면 분할 수단을 새로 설계하기 전에 **한 번 그대로 해보고** 결과를 `home/HARNESS-LOG.md`에 남긴다(`docs/workflow-spec.md` R23 무효화 조건). 과거의 계획서 경로는 git 이력(2026-10-01 이전)에 있다.

조사가 직접 읽기를 크게 요구해 인터뷰 컨텍스트가 200k를 넘으면, 멈추고 스펙 파일을 저장한 뒤 `/clear`를 건넨다 — 스펙 리뷰와 ③은 새 세션에서 한다. 그건 폴백이지 기본값이 아니다.

출력 형식과 가독성은 현재 활성 output style의 규칙을 따른다.
